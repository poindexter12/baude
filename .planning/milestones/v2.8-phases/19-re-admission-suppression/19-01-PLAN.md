<objective>
Lead the phase with one tracer slice: a repository removal travels through `removal::remove`, reaches a new fourth clearing stage after the save commits, deletes the removed folder's entry from `folder-workspaces.json` through the existing `locked_merge_write` merge path, and reports what it cleared in `RemovalReport`. Then expand the same slice to checkout and standalone keys, to the no-binding standalone no-op, and to best-effort failure reporting.

Purpose: READM-01 is the first of the three places a removed row can come back from (CONTEXT "Specific Ideas"). Proving the stage shape, the report fields and the preview agreement on this one path first means plans 03 and 04 only add kinds to a working stage instead of inventing the stage under the marker and suppression work. The helper is business logic with crisp input and output (key in file, key not in file, file absent), so TDD fits.
Output: `folder_workspace::clear`, the clearing vocabulary (`ClearingKind`, `ClearedItem`, `ClearingFailure`), `RemovalReport.cleared` and `RemovalReport.clearing_failures`, `planned_clearings`, `clear_stage` wired after `persist_stage`, preview parity, and the tests named below.

<feature>
  <name>Binding clear as the fourth removal stage, with report and preview parity</name>
  <files>baude-core/src/removal.rs, baude-core/src/folder_workspace.rs</files>
  <behavior>
    - `folder_workspace::clear(Some(root), folder)` on a file holding `folder_key(folder)` removes that entry, keeps every other entry, keeps `schema_version` at `SCHEMA_VERSION`, and returns `Ok(true)`
    - `clear` on a file lacking the key returns `Ok(false)` and performs no write; on an absent file it returns `Ok(false)` and the file stays absent; with `root = None` it returns `Ok(false)`
    - `remove(RemovalTarget::Repository(key))` clears the key for the repository's `observed_main_worktree` and for each removed checkout's `observed_path`; `remove(RemovalTarget::Checkout(key))` clears that checkout's `observed_path`; `remove(RemovalTarget::Standalone(key))` clears its `canonical_path`
    - The real-run report lists each removed entry as `ClearedItem { kind: ClearingKind::Binding, path }`; a merge-write error lands in `clearing_failures` as `ClearingFailure { kind: ClearingKind::Binding, path, error }` and `remove` still returns `Ok`
    - `preview_removal` returns `cleared` equal to `planned_clearings(state, &set)` and empty `clearing_failures`; it still writes nothing and signals nothing
  </behavior>
  <implementation>`clear` mirrors `record` (same `folder_key`, same `locked_merge_write`, `remove` instead of `insert`) with a `load_json` pre-check so an absent key or absent file causes no write. In `removal.rs`, `planned_clearings` is a pure function of `&RepositoryState` and `&RemovalSet`; `clear_stage(planned: &[ClearedItem]) -> ClearingResults` executes the Binding items, returns `ClearingResults { cleared, failures }` and never `Err`; it takes only the planned list, because any parameter it does not read would fail Task 3's `clippy -D warnings` gate, and plan 04 widens the signature to `(removed: &RemovedRows, state: &RepositoryState, planned)` when it binds the `RemovedRows` return of `candidate.remove_rows` for the marker and suppression work; `remove` passes `clearing` into `StageResults`; `report_from_set` copies the results into the two new report fields.</implementation>
</feature>
