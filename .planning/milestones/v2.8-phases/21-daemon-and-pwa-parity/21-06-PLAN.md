<wire_contract>
## Status handling, restated from the 21-03 matrix (`21-03-PLAN.md`, the table under its status section)

| Daemon answer | Arrives as | TUI outcome after a preview | TUI outcome after an execute |
|---------------|-----------|------------------------------|-------------------------------|
| 200 report | `Report` | open the confirmation | close, footer notice from the report |
| 409 fresh report | `Drift` | treated as `Report` | re-install the confirmation with the fresh report |
| 404 plain text | `Gone` | close, `already removed` notice | close, `already removed` notice, no retry |
| 500 or 503 plain text, 503 includes text beginning `repository busy:` | `Refused` | close, footer notice with the daemon's text | keep the confirmation open with the daemon's text, Enter retries |
| no answer to a preview | `Unreachable` | close, footer notice, nothing was asked to change | handled as unknown outcome if it ever arrives |
| no answer to an execute | `Indeterminate` | handled as `Unreachable` if it ever arrives | `rows_gone` true: close and report removed; false: unknown outcome, Enter previews again |

D-09 is option B: `checkout_key` exists only on `GET /rows`, and the TUI joins a `/sessions` row to
its key on `session_id`.
</wire_contract>

<error_text_register>
## Recorded decision: error-text register for the three clients

The three clients are the TUI on local rows, the TUI on remote rows, and the PWA. Decided once, here:

1. The message is the daemon's body, or core's `RemovalError` display text for a local row. No
   client rewords, classifies or translates it. Statuses drive behaviour; text is for reading.
2. A row key in Rust debug form, such as `Checkout(CheckoutKey(3))`, never reaches the user. A
   client substitutes the row's label from its own index, display name plus branch where the row
   has one, and the words `unknown row` when its index cannot name the key. `unknown row` is the
   label 21-07 already pins for the PWA.
3. Paths inside the text stay exactly as sent. `tilde_path` (`baude/src/ui.rs:1360`) is not applied:
   a remote path is under another host's home, and the modal's own path sections already print
   `path.display()`.
4. Text is made safe for the surface it lands on: control characters stripped and length capped in
   the TUI (21-08 `sanitize_daemon_text`), escaped in the PWA.

Where it holds: both TUI origins, by Task 3 of this plan, and the PWA, by 21-05. `bauded/web/*` is
21-05's and this plan does not change it. 21-05 Task 2 implements the PWA share of rule 2: a
module-private `userText` in `removal-controller.js`, behind `setError` and `say`, the only writers
of `errorText` and of notices, replaces each `Checkout(CheckoutKey(n))`-style token with the row's
`/rows` label, or with `unknown row` for a key the index cannot name, and changes nothing else. It
is pinned there by `error_text_names_a_known_row_by_label`,
`error_text_reads_unknown_row_for_a_key_the_index_cannot_name`,
`error_text_without_a_key_token_is_unchanged` and
`notice_text_names_a_row_removed_by_the_same_response`. No share of the rule is left without an
owner.

Not done, with reason: changing `RemovalError`'s `Display` in `baude-core/src/removal.rs:257`. That
would fix every client at the source, but no Phase 21 plan owns that file, 21-01 keeps daemon bodies
as that display text per D-03, and core holds keys, not names, so the result would still need a
client-side label.
</error_text_register>

<test_fixture_rules>
## Rules every test in this plan follows

- The daemon is the 21-08 scripted double, `remote::test_double::serve`, and the app holds
  `RemotePoller::idle(double.base())`. Never `RemotePoller::start` in a test: its background poll
  races the script (codex MEDIUM). An idle poller starts no thread, so its `snapshot()` and `rows()`
  are never fed. Tests put the remote view in place with `App::apply_remote_view` and drive the
  wait with `App::poll_remote_removal`.
- Every test ends by asserting `double.unscripted()` is empty. A request to a path or method the
  test did not script must fail the test, never match loosely.
- Request counts come from `Double::requests()` or `Double::request_count()`. This plan defines no
  counter of its own (claude LOW).
- The preview report the double serves is a real one: built by core over a real git fixture through
  the existing local preview, never typed by hand. The `/rows` body reuses the shape the 21-08 tests
  in `baude/src/remote.rs` send, changing only names, keys and `session_id`.
- The remote row's checkout key is deliberately the same number as a local row's key. Two machines
  hand out small integers independently, so this collision is the normal case, not a corner.
- Assertions read app state, the double's recorded requests, or rendered text. No test greps source.
- Baselines measured at HEAD on 2026-11-11: `app::tests::remote_remove_` matches 0 tests,
  `app::tests::d_on_remote_row_` 1, `app::tests::sidebar_action_d_` 2, `ui::tests::remote_removal_modal_`
  0, `ui::tests::removal_text_` 0. Every verify below looks for a named `... ok` line that does not
  exist at HEAD, so no gate here passes before the work is done.
- Commit subjects and bodies carry no parentheses other than the conventional scope. release-please
  skips a commit with nested parentheses without saying so.
</test_fixture_rules>
