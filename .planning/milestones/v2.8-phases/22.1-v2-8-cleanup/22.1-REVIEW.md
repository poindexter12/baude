## Summary

I reviewed `git diff 30089e4..HEAD` for the files in scope. I skimmed the mechanical fixture conversions for a `FixtureRoot` dropped as a temporary or an assertion that changed. Those files are backend/claude.rs, breadcrumbs.rs, folder_workspace.rs, git.rs, hook.rs, launch.rs, marker.rs, meta.rs, persist.rs, workspace.rs, worktree_scan.rs, main.rs, ui.rs, push.rs and transcript.rs.

**WR-06 locking (priority 1).** The exclusion holds. Every route that can change a reserved repository or folder goes through the reservation:
- plain admission, both the `JoinStored` and the `Discovered` arm
- `ReuseStandalone`
- worktree activation
- `remove`, `restart` and `set_archived`, through `session_busy`

The routes that change one session look the session up in `self.sessions`, so they cannot reach a session that has been moved out. These are messages, keys, interrupt, permission and resize. The poll thread's only write to `repository_state` is the `resume_id` clear, which does not change which rows a removal selects. So `SelectionChanged` cannot happen in production. Other checks that passed:
- **Lock order:** manager mutex, then the reservation table, with no reverse edge.
- **No deadlock:** no `MutexGuard` crosses an await, and the pause gate is test-only.
- **Reservations:** they bind as named fields (`_repository_reservation`, not `_`), so they are released at the end of `finish_removal`, after the publish. On early returns they drop at return, and during an unwind they drop as well.
- **Publish:** the single non-test `publish` sits after the successful `commit`.
- **503 mapping:** correct for `Busy`, `FolderBusy` and `MutationError::Busy` on all four session routes, including the custom `restart` mapper.
- **Redirects:** the test redirects are captured before `spawn_blocking` and installed inside it.

The gap is panics outside the `catch_unwind`: see WR-01.

**removal.rs stage split (priority 2).** `remove()` is `prepare`, then `stop_and_delete`, then `commit`, run back to back on the same `state`. The extra `reselect` and the second `candidate_without` therefore cannot diverge for the TUI. `select_rows` probes only `symlink_metadata`, and `reselect` compares row keys only, so the disk stage's deletions do not trip it. `commit` rebuilds the candidate from live state as intended.

**Test reaper (priority 3).** The session sweep cannot reach session 0 or 1, the harness's session or its process group. The `FixtureRoot` drop is safe: the path is private, built from a prefix checked in `new`, and checked again in drop. `remove_dir_all` and `make_owner_writable` never follow symlinks. The reaper does not verify identity, so pid reuse can reach a stranger's process group or session: see WR-02.

**Scripts and CI (priority 4).** Exit codes are captured directly. A signal is mapped to 128+n. An internal error or a sampler failure exits 2 and never reads as a pass. An empty `mktemp` result is refused, because the empty path resolves to the checkout. The job name `check` and its matrix are unchanged, so the required check names are unchanged.

**Suppression, PWA and service worker (priority 5).** `lift_key` is shared correctly by both call sites. The title logic matches the README. The cache bump to `baude-v8` is consistent with the activate handler, which deletes every other cache. Minor rendering and transient-404 notes are listed under Info.

## Warnings

### WR-01: A panic in stage one or three loses the moved-out runtime handles and leaves the registry inconsistent

**Status:** fixed in c11a432. `begin_removal` runs core's `prepare` in `catch_unwind` and puts the handles back on a panic. `finish_removal` runs its body in one `catch_unwind` with the handles owned outside it, and `recover_from_commit_panic` returns every handle core did not consume. When core's commit had already replaced the state, it also drops the removed rows' registry entries. Both answer 500 naming the panic, through `PreparePanicked` or `CommitPanicked`, and nothing is published. Tests: `removals_panic_while_preparing_restores_handles`, `removals_panic_in_the_save_restores_handles` and `removals_panic_after_the_commit_keeps_the_registry_consistent`.

**File:** `bauded/src/manager.rs:1405-1413`, `bauded/src/manager.rs:1501-1532`, `bauded/src/api.rs:199-212`

**Issue:** Only stage two runs inside `catch_unwind` (`RemovalInFlight::stop_and_delete`, `manager.rs:265-273`). Two other spans own the moved-out `Session` values in a local `Vec<RowRuntime>` with no unwind protection:
- in `begin_removal`, after `collect_row_runtimes` (`:1405`) and through `removal::prepare` (`:1407`)
- all of `finish_removal`, including `removal::commit`, the save closure (`persist::save_*`), `clear_stage`'s filesystem and git work, and `restore_row_runtimes`

A panic in either span unwinds through `spawn_blocking`, and the handler answers `500 removal task failed`. The state it leaves behind:
- The `Session` values are dropped, not put back in `self.sessions`.
- `runtime_checkouts` and `runtime_standalones` still map the rows to the dropped ids, so `session_busy`, `stored_row_path` and `rows()` resolve to sessions that no longer exist.
- The reservation is released by the unwind, so the repository is open again while its state is inconsistent.
- The manager mutex is poisoned, but `lock()` recovers it with `into_inner` (`manager.rs:452-454`), so the daemon goes on serving that state.

The doc comments say the opposite: the handles "stay owned by `self` whatever happens, for `finish_removal` to commit or put back", and `finish_removal` says every error path returns "every runtime handle to the registry". The phase brief asked for exactly this property ("every error and panic path restores runtime handles"), and it does not hold for stages one and three.

**Fix:** Give the moved-out handles one owner whose drop puts them back. Options:
- A guard type that holds `&mut Manager` plus the `Vec<RowRuntime>` and calls `restore_row_runtimes` in `Drop` unless disarmed after a successful commit.
- At minimum, wrap the `removal::commit` call in `catch_unwind(AssertUnwindSafe(..))`, with `runtimes` borrowed from outside the closure, and map a panic to `SlowStagePanicked`-style handling after `restore_row_runtimes(runtimes)`.

Add a test that arms a panic in the save closure (`persistence_target_for_test` already has a seam) and asserts that `/sessions` lists the id again.

### WR-02: `RuntimeReaper` signals a recorded group or session without checking for pid reuse

**Status:** fixed in fd1ebef. The reaper keeps the recorded start time. Before each round of signals it inspects the process holding the pid, as `Pty::signal_verified` does. It skips the group kill when a live process holds the group id and is not the recorded leader. It skips the sweep when the leader's pid now names another process. It signals nothing when the pid cannot be inspected. The rule that it sweeps only a session the leader leads is kept. Test: `runtime_reaper_signals_nothing_when_the_leader_pid_was_reused`.

**File:** `baude-core/src/testing.rs:739-752`, `baude-core/src/testing.rs:788-830`

**Issue:** The reaper stores `leader`, `process_group` and `session` from the `ProcessIdentity`. It drops `start_time` (`for_identity`, `:721-727`). At drop time it sends `kill(-process_group, SIGKILL)` without condition, then SIGKILLs every live pid whose `getsid` equals the recorded session. Many call sites bind the reaper at the start of a test and drop it seconds later, after the test itself killed and reaped the leader through `DELETE /sessions`, `remove`, `kill_all` or `restart`. Examples are the `_reapers` in `api.rs` around `:1218`, `:1387` and `:1539`, and in `manager.rs` around `:5062` and `:5603`.

Once the leader is reaped and its group is empty, the kernel may hand that pid out again. It becomes a stranger's group id as soon as any process with that pid calls `setpgid`, which every job an interactive shell starts does. It becomes a stranger's session id as soon as such a process calls `setsid`, which every terminal tab, ssh login and PTY child does. The reaper then SIGKILLs a developer's foreground job or a whole terminal session. When a developer runs plain `cargo test` in parallel, it can also kill another test's PTY session, which makes that test flaky.

This needs pid wrap-around. That is plausible on macOS, where pids wrap at 99,999 and the suite spawns a lot of git. The consequence is SIGKILL of an unrelated user process. Production code already guards this exact hazard: `Pty::signal_verified` checks pid and start time through `session::inspect_process_identity` (`pty.rs:684-695`) before it signals.

**Fix:** Keep `start_time` in the reaper.
- Before `kill(-pgid)`: if a live process has pid == `process_group` and its `inspect_process_identity(..).start_time` differs from the recorded one, skip the group kill. While the original group still has members, its pgid cannot be reused, so an orphaned member is still reached.
- Before the sweep: apply the same check to the session leader pid. If a live process has pid == `session` with a different start time, the session id was reused; skip the sweep.

Add a test that builds an identity with a live pid and a wrong `start_time`, and asserts that nothing is signalled. `runtime_reaper_never_sweeps_a_session_it_does_not_lead` is the template.

### WR-03: An early-resume reconcile refused as busy is lost if the removal window outlasts 3 s

**Status:** fixed in 2f24774. A reconcile refused as `Busy` goes into `pending_early_resume_reconciles` with the spawn time of the runtime that exited. Every tick retries it until it runs, whether or not the window is still open. The entry is dropped once the session is gone or runs a newer runtime, and kept while a removal holds the session out of the registry. A `Busy` refusal is no longer logged. Test: `poll_runs_a_deferred_early_resume_reconcile_after_the_window_closed`, which holds the repository past the window.

**File:** `bauded/src/manager.rs:4231-4276`, `baude-core/src/session.rs:117-121`

**Issue:** `reconcile_early_targeted_resume_exits` clears `saved.session.resume_id` in `repository_state` and then calls `self.remove(id)`. Since this phase, `remove` answers `MutationError::Busy` while a removal holds the session's repository (`:3588-3590`), and the manager lock is now free during the slow stage, so the poll thread can meet that reservation. The error is only printed (`:4273-4275`). The retry depends on `early_targeted_resume_exit()` still holding on a later tick. That needs `now - spawn_unix_ms <= EARLY_RESUME_ID_EXIT_WINDOW_MS`, which is 3,000 ms (`session.rs:42`).

A slow stage that kills several runtimes with graceful teardown and runs `git worktree remove` can easily take longer than 3 s. In that case the exited sibling session is never torn down. It stays registered as exited and its row keeps its runtime until a user acts. The poll also logs `failed to reconcile early targeted resume: repository busy` once a second for the whole window.

The 22.1-10 and 22.1-11 summaries record this as backlog. It is a regression this phase introduced: it could not happen while the removal held the manager lock. The test `poll_defers_an_early_resume_reconcile_while_its_repository_is_busy` only covers a hold shorter than the window.

**Fix:** When `remove` returns `Busy`, record the id in a `pending_early_resume_reconcile: HashSet<u64>` on the manager and retry it on every tick until it succeeds or the session is gone, independent of the 3 s window. Skip the log line on `Busy`. Extend the test to drop the hold only after `EARLY_RESUME_ID_EXIT_WINDOW_MS` has passed.

## Info

### IN-01: A failed removal can leave two sessions with the same name

**File:** `bauded/src/manager.rs:3121-3133`, `bauded/src/manager.rs:1465`

**Issue:** `unique_name` scans only `self.sessions`. During the window the doomed sessions are out of the registry, so a `POST /sessions` in another repository can take a doomed session's name. If the removal then fails, `restore_row_runtimes` puts the original back, and two live sessions share one name. Names are not validated as unique, but the daemon otherwise keeps them unique (`duplicate_names_get_suffixed`).

**Fix:** Have `unique_name` also consult the stored names of rows whose runtime is in `runtime_checkouts` or `runtime_standalones`. Those entries are kept through the window.

### IN-02: Push notifications fire again for sessions restored after a failed removal

**File:** `bauded/src/notify.rs:53-60`, `bauded/src/main.rs:247-252`

**Issue:** The poll thread passes `m.list()` to `Notifier::tick`, which forgets the notified state of every id missing from the list. During the window the doomed sessions are missing. If the removal fails and they come back, a session that is still `waiting` or `exited` triggers a second push for the same state.

**Fix:** Have `list()` or the notifier input include sessions held by an in-flight removal, or have the notifier keep state for ids that `runtime_checkouts` or `runtime_standalones` still map.

### IN-03: Before the first `/rows` body arrives, every session is listed under "other sessions"

**File:** `bauded/web/app.js:148-153`, `bauded/web/app.js:716-724`, `bauded/web/removal-controller.js:511-525`

**Issue:** `refresh()` starts `loadRows()` without awaiting it, then assigns `/sessions`. Until the first `/rows` body lands, the controller's rows are the empty snapshot. `unclaimedSessions` then claims nothing, so the first paint lists every session, the repository-owned ones included, under an `other sessions` heading. The test pins this (`unclaimedSessions(null, sessions)` returns all ids). A newly created session sits under that heading until the next `/rows` load. Before this change the same case showed a flat list with no misleading heading.

**Fix:** Do not render the `other sessions` heading, or fall back to the flat list, until the controller has applied at least one fetched `/rows` body.

### IN-04: Session-scoped routes answer 404 during the window; the PWA treats that as "session is gone"

**Status:** no longer true since fb34c5c, which carries out the owner's decision. Every single-session route of a doomed session now answers the busy 503 during the slow stage, then 404 after the commit, and serves the session again after a failure. An open `stream` or `activity-stream` stays open through the window. The PWA retries the chat view on a 503. Tests: `removals_doomed_session_routes_are_busy_then_gone`, `removals_doomed_session_routes_come_back_after_a_failure` and the node test `session_request_outcome_reads_a_busy_503_as_transient`.

**File:** `bauded/src/manager.rs:1638-1662`, `bauded/web/app.js:232-234`

**Issue:** During the slow stage the doomed sessions are out of `self.sessions`. So the following routes all answer the "no session" 404:
- `GET /sessions/{id}`, messages, queue, keys, interrupt and permission
- hook ingestion (`ingest_event`)

The PWA's chat view handles a 404 with `location.hash = "#/"; toast("session is gone")`. A user watching that session on another device is sent back to the list, and hook events posted in the window are dropped. If the removal then fails, the session comes back, but the view and the events are lost. The README sentence "Every other route keeps its status codes" is literally true, since 404 already existed on those routes, but it hides this; the 22.1-11 SUMMARY lists it as an open item.

**Fix:** Have `session(id)` answer `MutationError::Busy` or 503 for an id that `runtime_checkouts` or `runtime_standalones` maps but `sessions` lacks, as `session_busy` already does for four routes. Or document the 404 in the README with a test.

### IN-05: The leftover check cannot see a runtime leaked outside TMPDIR

**File:** `scripts/assert-no-test-leftovers.sh:280-291`, `bauded/src/manager.rs:5056-5065`

**Issue:** Orphans and live processes are recognised only by a cwd under the TMPDIR handed in. Some tests spawn runtimes elsewhere. For example, `create_list_info_remove` runs `m.create("/tmp", ...)`. On macOS, both CI and local, TMPDIR is `/var/folders/...` and not `/tmp`. A `sleep 30` leaked from such a test passes `command=0 orphans=0 live=0`, so "suites leave no stray runtime processes" is not proven for these tests.

**Fix:** Point those tests at a `FixtureRoot`. Alternatively, also flag non-descendant processes whose command matches the fixture runtime doubles (`sleep 30`) and whose parent is pid 1 or a subreaper.

### IN-06: The sampler never prunes `first_seen`, so a reused pid can be reported as an orphan

**File:** `scripts/assert-no-test-leftovers.sh:285-291`

**Issue:** The key is `(pid, command)`, and entries are never removed when the process disappears. A transient non-descendant `sleep 30` might be seen once, for example between the leader's death and the reaper's sweep. If a later transient `sleep 30` gets the same pid at least 5 s later, it is reported as an orphan the moment it is sampled. This gives a false failure, not a masked one.

**Fix:** At the end of each `sample()`, drop `first_seen` keys whose pid was not present in that snapshot. Alternatively, key on the pid plus its start time (`/proc/<pid>/stat` field 22, or `ps -o lstart=`).

### IN-07: The new suite step can block without bound, and the `check` job has no timeout

**File:** `scripts/assert-no-test-leftovers.sh:181-205`, `scripts/assert-no-test-leftovers.sh:293-295`, `.github/workflows/ci.yml:13-18`

**Issue:** `darwin_snapshot` runs `lsof` and `ps` through `subprocess.run` with no `timeout`. `Sampler.stop()` then `join()`s with no bound. A stuck `lsof`, which on macOS can block on an unresponsive mount since `-b` is not passed, hangs the step after the suite has finished. The `check` job sets no `timeout-minutes`, so CI holds the runner for the 6-hour default. The missing job timeout predates this phase; the unbounded watcher is new.

**Fix:** Pass `timeout=` to both `subprocess.run` calls and raise `InternalError` on `TimeoutExpired`. Add `-b` to `lsof`, join the sampler with a bound, and set `timeout-minutes` on the `check` job.
