# Phase 22.1 Plan 07: shared suppression lift key Summary

The TUI and the daemon now lift a suppression entry by the same core key, `suppression::lift_key`. That key is the checkout root git reports for the opened path. Before this plan, a daemon admission of a subfolder of a checkout left the checkout's entry in the store. That case was shown failing, then fixed. Four new tests pin the key and the store that both clients share, and the README describes the store.

## What was built

- **`suppression::lift_key(admitted)`** returns `git::repo_root`, else `admitted.canonicalize()`, else the path as given. Its doc comment states the residual case: a daemon row stored on a subfolder writes its entry on that subfolder. Nothing ever lifts that entry, and nothing reads it either.
- **Daemon:** `lift_admission_suppression` lifts `lift_key` of the stored row path. The doc comments on `create` and the lift say the key is the checkout root. `create` is otherwise unchanged: the lift still runs once, after `admit` returned Ok, and only when persisting.
- **TUI:** `App::lift_suppression` lifts `suppression::lift_key(path)`. Its own `repo_root` fallback is gone.
- **README:** a new paragraph in "What baude forgets" covers:
  - when the TUI and a daemon share the store
  - that a removal or an explicit opening in either client applies to both
  - that the lift uses the checkout root
  - that a daemon run from compose keeps its own store
  - that a removed daemon subfolder row leaves an entry nothing reads

  "Removing rows in the PWA" gains one sentence.

README paragraph as committed:

> The TUI and a daemon on the same machine share the suppression store when they use the same config dir and the same workspace. A removal in either keeps the row out of the TUI's sweep. Opening the folder in either lifts the entry for both: in the TUI with `n`, `c` or a launch inside it, on the daemon with `POST /sessions` or the PWA's new session. The entry lifted is the one for the checkout root of the folder you opened, so opening a subfolder of a removed worktree lifts that worktree's entry. A daemon run from the compose file keeps its own config volume, and so its own store. A session the daemon opened in a subfolder of a checkout is stored on that subfolder, and removing it writes an entry for the subfolder that nothing reads.
