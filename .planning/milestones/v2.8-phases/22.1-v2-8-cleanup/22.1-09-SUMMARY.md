Every path that could change a reserved repository or folder now answers 503. That covers a second removal of a folder, a plain `POST /sessions` into a reserved repository or onto a reserved folder row, worktree creation on a reserved repository, and `DELETE`, `restart`, `archive` and `unarchive` of a session in one. The body names the stored main checkout or the folder. All of this still runs under today's manager lock, so plan 22.1-10 can release the lock without opening a window. ## What was built

- **`StandaloneReservations`** in `bauded/src/manager.rs` has the RAII shape of core's registry: an `Arc<Mutex<HashSet<StandaloneKey>>>`, `reserve(key) -> Result<StandaloneReservation, ()>` and `is_reserved(key)`. The guard owns its `Arc` and removes its key on drop. It is a `Manager` field next to `repository_reservations`. The test seam is `reserve_standalone_for_test`.
- **`remove_rows`** reserves the standalone key for a `RemovalTarget::Standalone`, after the repository reservation and before the recheck. A refusal is `RemoveRowsError::FolderBusy(key)`. The guard lives until the method returns. `execute_removal` builds the body under the lock through `Manager::standalone_path`. `removal_error` maps `FolderBusy` to 503.
- **`MutationError::Busy(String)`** carries the whole body. `mutation_error` and the `restart` handler map it to 503. The body comes from `repository_busy(key)` or `folder_busy(key)`, which read `repository_path` or `standalone_path` and fall back to the key's Debug form.
- **`admit`**:
  - The `ReuseStandalone` arm refuses a reserved key before `reopen_standalone`.
  - On the plain path, after the route match, `JoinStored(key)` reserves `key`. `Discovered` reserves the stored repository whose `observed_common_dir` equals the discovered common dir. The guard lives until `admit` returns. A refusal is `repository_busy`.
  - The worktree branch returned earlier and is untouched apart from mapping `LifecycleOutcome::Busy { repository }` to `repository_busy(repository)`.
- **`RepositoryReservations::is_reserved`** in core answers true for a held guard of either kind.
- **`Manager::session_busy(id)`** resolves the id through `runtime_checkouts`, then the checkout's `repository_key`, or through `standalone_owner`. It returns the busy error when that repository or folder is reserved. `remove` calls it first, `restart` calls it right after the persistence check, and `set_archived` calls it first, so no `self.session(id)` lookup comes before it.

### No double reservation

I read the code to confirm that nothing reserves the same repository twice:
- Inside the plain admission's guard, `ensure_runtime_capacity`, `unique_name`, `record_checkout_intent`, `save_checked`, `spawn_retained_with_mode` and `spawn_with_mode_internal` call no `reserve` or `reserve_reopen`. The only reservation sites in `manager.rs` are the four `reconcile_*` and `retry_*` sites, `remove_rows`, `activate_branch_worktree`, `prepare_remove_worktree`, `confirm_remove_worktree`, `reopen_checkout` and the two test seams.
- The worktree path returns before the new reservation and still reserves once, inside `activate_branch_worktree`.

Two tests pin this, beyond the plan's assertions:
- `busy_repository_worktree_create_is_503` ends with the same worktree `POST` answering 201 once the hold drops, and branch `topic` then exists.
- `busy_repository_plain_admission_is_503_and_stores_nothing` ends with the linked worktree `POST` answering 201.

A second reservation of the same repository on either path would answer 503 there.
