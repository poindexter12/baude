## What was built

**`removals_same_repository_is_busy_during_the_slow_stage`** uses `removal_fixture_two_checkouts`: a main checkout and a managed worktree `topic`, each with a live session. The removal of the worktree is paused. Once the pause reports one entrant and the mutex is free, the probe thread does these, in order:
- previews the main checkout, which is served with 200
- executes that fresh preview
- plain `POST /sessions` on the main checkout path
- `POST /sessions` with worktree `second`
- archive of the main checkout's session
- DELETE of the main checkout's session
- DELETE of the doomed session, which is out of the registry
- `GET /sessions`, which lists only the main session

Every request except the preview and the read answers 503 with exactly `repository busy: <main checkout>`, within 2 s. After the release:
- the removal answers 200 with one `rows_removed` event
- the doomed agent is gone and the main agent is alive
- `/rows` holds one checkout
- branch `second` does not exist
- a fresh removal of the main checkout answers 200 with one more event

**`removals_standalone_is_busy_during_the_slow_stage`** uses `folder_fixture`. The removal is paused. During the window, the same report executed again and `POST /sessions` on the folder both answer 503 `folder busy: <folder>`. The window's `/sessions` lists no id beyond the ones listed before the pause. After the release:
- the removal answers 200 with one event
- the agent is gone and `/sessions` is empty
- the `standalone` array is empty
- the folder is untouched

**`removals_failure_in_the_slow_stage_leaves_rows_and_handles`** uses `removal_fixture`. `fail_next_agent_teardown_for_test(id, "agent stop refused once")` is called in its own statement before the pause is armed and before the removal starts, so the guard drops before the removal begins. Then the test reads `/rows` and `/sessions` and subscribes to events. The probe reads `/rows` in the window, and it equals the body read before the removal. Results:
- the removal answers 500 with a body naming `agent stop refused once`
- `/rows` equals the earlier body
- `/sessions` is `[id]` and the agent pid is alive
- no event arrives within 500 ms
- a fresh preview names the same agent pid, executes with 200, and publishes exactly one event

The failure is hit inside the slow stage: the injection is keyed by pid and consumed in `Pty::kill_and_wait`, which `removal::stop_and_delete` reaches only after the pause, inside the same `catch_unwind` closure.

Helpers, all test-only:
- `delete_request(id)`
- `assert_window_busy`: asserts every status first, then every body and the 2 s bound
- `window_session_ids`

## README

The 503 row now reads: "refused on the daemon's own state. From `POST /removals`: the repository or folder is busy with another removal, a save of the daemon's state is blocked or failed, or a runtime handle is missing. From the session routes listed below: the repository or folder is busy with a removal". The 500 row adds "or the removal panicked while stopping runtimes and deleting worktrees".

New paragraph after "Every error body is plain text except the 409.":

> Other requests are served while a removal stops runtimes and deletes worktrees. `GET /rows` keeps listing the rows being removed until the removal commits, then drops them all at once. `GET /sessions` stops listing the sessions being removed while the removal runs, and lists them again if it fails. A request that would change the repository or folder being removed answers 503 with the body `repository busy: <path>`, naming the repository's main checkout, or `folder busy: <path>`. Those requests are `POST /removals` for any of its rows, `POST /sessions` into it with or without a `worktree` branch, and `DELETE`, `restart`, `archive` and `unarchive` of its sessions. Creating a worktree in a busy repository used to answer 400 and now answers this 503. `POST /removals/preview` is still served during a removal and reads the rows as they were. Every other route keeps its status codes.

Each claim maps to a test:
- rows stable, then gone: `removals_rows_shape_is_stable_during_the_slow_stage`
- sessions hidden: the window `/sessions` reads in both busy tests
- sessions listed again on failure: the failure test and the panic test
- busy bodies: the two new tests and the 22.1-09 `busy_` tests
- 400 to 503: `busy_repository_worktree_create_is_503`
- preview served: the repository busy test
