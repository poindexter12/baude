<objective>
Add the PWA approve/deny card: a card above the composer in the chat view that appears while a permission is pending, shows the tool + an input summary, and POSTs the decision to `/sessions/{id}/permission` — disappearing once resolved. Output: the `perm-card` render + approve/deny handlers + the `GET /permission` fetch on chat open and on a permission push/SSE, in `bauded/web/app.js`; an `sw.js` cache-version bump so the new asset ships.

In `bauded/web/app.js`:

**Fetch the pending permission.** Add a `fetchPermission(sid)` that calls `api(\`/sessions/${sid}/permission\`)` (GET) and stores the result on `state.pendingPermission` (null when none). Call it (a) on chat open (where the activity fetch already runs on open), and (b) when a push/SSE update reports `waiting_reason === "permission"` for the open session. On any update where `waiting_reason !== "permission"`, set `state.pendingPermission = null`. Use the existing `api()` GET shape (mirror the activity fetch at ~223).

**Render the card.** In `renderChat()`, build a `permCard` string gated on `s && s.waiting_reason === "permission" && state.pendingPermission`:
a `<div class="perm-card">` containing the tool name and an input summary (a small `permSummary(input)` helper — stringify/clip the input object to a short readable line), Approve and Deny buttons. **`esc()` EVERY dynamic string** (the tool name and the input summary are attacker-influenced via Claude's tool args — XSS, RESEARCH Pattern 5 / Anti-Pattern). Insert `${permCard}` in the `$app.innerHTML` template BETWEEN `${activityStrip}` and the `<form id="composer">` (CONTEXT: "above the composer").

**Wire the buttons.** In the same handler block where `escbtn`/`killbtn` onclick are attached (~630-641), wire `#permallow`/`#permdeny` to an `approve()`/`deny()` that calls `api(\`/sessions/${state.sid}/permission\`, {method:"POST", body: JSON.stringify({decision})})`, then OPTIMISTICALLY `state.pendingPermission = null; render();` and re-`fetchPermission(state.sid)` to confirm it cleared (CONTEXT SC3: the card disappears on resolve). On error, `toast(...)` like `interrupt()` does. **Deny denies the single tool call only — it must call the permission POST with `{decision:"deny"}`, NOT the interrupt/kill route** (CONTEXT: deny does not kill the session; Claude continues with the tool denied).

Add minimal CSS for `.perm-card`/`.perm-actions`/`.allow`/`.deny` consistent with the existing PWA styles (reuse existing button classes where possible).

In `bauded/web/sw.js`: bump the cache-version constant so the updated `app.js` (and any styles) ship to the installed PWA — mirror the 03-03 sw.js cache-bump precedent.

Do NOT call the interrupt/kill route on deny. Do NOT inject any dynamic string without `esc()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude tool args → PWA card | the tool name + input are rendered in the card; they originate from Claude's tool call and may contain HTML metacharacters — XSS sink. |
| PWA → POST /permission | the decision crosses to the daemon; the daemon validates decision ∈ {allow,deny} (04-02). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-13 | Tampering (client) | perm card render | mitigate | `esc()` EVERY dynamic string (tool name, input summary) before injecting into innerHTML — the established PWA XSS rule; the card injects arbitrary tool input. |
| T-04-14 | Elevation of Privilege | deny action | mitigate | Deny POSTs `{decision:"deny"}` to `/permission` (denies the single tool call), NOT the interrupt/kill route — Claude continues with the tool denied; no over-broad action. |
| T-04-15 | Spoofing | POST /permission from PWA | accept | Inherits the project tailnet/loopback bind (same as the other REST routes); no auth layer by design (single-user). |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No package installs this phase — vanilla JS, no build step, no new assets beyond app.js/sw.js edits. |
</threat_model>
