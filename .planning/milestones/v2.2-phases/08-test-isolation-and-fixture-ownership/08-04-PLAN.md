<objective>
Build the enumeration and classification core for leak preview: walk the real managed
worktrees root, filter by path shape, classify each candidate from layered evidence, and
default every unproven candidate to `Indeterminate`.

Purpose: 1433 `repository-N` directories sit under the developer's real data root today.
The tooling that looks at them must be incapable of authorizing a deletion on weak
evidence, because the two weakest signals available — matching path shape, and a missing
gitdir — are each satisfied by directories that are provably live.

Output: `baude-core/src/worktree_scan.rs`, production code (no test-support gate), with the
evidence model and the read-only enumeration. Plan 05 adds state cross-referencing, the
prune re-verification, and the CLI surface.
</objective>

<research_deviations>
**D-14 is corrected: path shape proves nothing on its own.** CONTEXT.md locks "ownership is
proven by strict path-shape match under the real worktrees base" and adds that "workspace
state has zero record of the leaked directories, so ownership cannot be sourced from
state." The live dataset contains direct counter-examples to the first claim and inverts
the second.

Four directories under `worktrees/claude/` match the identical shape and are not test
leaks: `repository-2/primary-2` holds a real 39-entry checkout for a repository the
developer actively uses, `repository-14/primary-14` holds another, and `repository-1` and
`repository-5` were created by *production* runs hours **after** the v2.1.4 containment fix
landed — they carry small sequential keys matching live entries in `state-claude.json`,
not the pid-derived keys the fixtures generate. The same shape therefore matches, at once,
1431 test leaks, two real managed worktrees holding real content, and two directories the
developer's own baude created that day.

So shape is a necessary filter and a sufficient condition for nothing. And state being
silent about the leaked directories is exactly what makes it useful: `SavedCheckout` records
`observed_path`, so a directory state *does* reference is definitively live. State is the
source of ownership-negative evidence, and plan 05 consumes it.

**A missing gitdir is the single most dangerous signal in the dataset.** All 1433 candidates
lack a gitdir at any level. Treating that as proof of ownership would authorize deleting
every one of them, including the two live production directories — precisely what TISO-04
forbids in its wording. It is recorded as evidence and is never sufficient.
</research_deviations>

---

This is the one irreversible decision in Phase 8. Every other choice here can be reverted by
editing code; a `Removable` verdict that a later `--prune` acts on destroys user data that
no revert restores. The predicate is therefore agreed before it is implemented, not
reviewed after.

**What is being decided:** the exact evidence set that permits `Verdict::Removable`.

**The proposed predicate** — a candidate is `Removable` only when *all* of the following
hold, and `Indeterminate` in every other case:

1. `ShapeMatch` — the path is exactly `<real base>/<workspace>/repository-<u64>` or that
   plus one child segment, with the `u64` parsed by `str::parse::<u64>()`, under a
   canonicalized real base.
2. `NotReferencedByState` — a complete config-directory inventory of all workspace state
   files (including workspaces without worktree directories and both legacy names) was
   successfully checked. Neither a saved repository key in its source workspace nor any
   saved checkout/repository path overlapping this candidate or its descendants references it.
3. At least one of `Empty` (no entries at any level) or `GitDisownsIt` (a gitdir exists,
   `discover_repository` ran, and the path is absent from git's own worktree inventory).

And none of the hard blockers is present: `ReferencedByState`, `ContainsCheckout`,
`IsSymlink`, or `StateUnreadable`. Incomplete or unreadable state inventory blocks clearing
across the entire scan, because state can reference paths in another workspace.

**The consequences to weigh:**

- Clause 2 makes an unreadable state file or failed inventory block clearing every candidate
  in the scan, not only its nominal workspace. Cross-workspace path references are supported.
  Inferring absence from a failed read could clear live repo parents, including recorded
  keys 1 and 5 whose observed main worktrees are outside the managed root.
- `NoGitdir` appears in the evidence list but is deliberately *not* in clause 3. All 1433
  candidates satisfy it. Including it would make the predicate a no-op.
- Under this predicate, the two live `claude` directories holding real checkouts are
  blocked by `ContainsCheckout`, and `repository-1` / `repository-5` are blocked by
  `ReferencedByState` once their keys are matched.
- The predicate is intentionally conservative: it will report many genuine leaks as
  `Indeterminate`. That is the correct failure direction for this phase — the deliverable
  is a preview a developer can inspect, not a cleanup.

Implementation remains blocked on an actual human response to this checkpoint. The
complete-state-inventory and repo-parent clarifications above are safety prerequisites,
not approval of the proposed clearing predicate; neither this revision nor auto-advance
settles the decision.

**Approve, or state a different predicate.** Implementation of `Verdict::Removable` does not
begin until this is settled.

Create `baude-core/src/worktree_scan.rs` and declare it in `baude-core/src/lib.rs` as an
ordinary module. This is production code — do not put it behind the test-support cfg. Note

Define an `Evidence` enum with one variant per independent signal: a shape match; a
not-referenced-by-state result carrying the list of workspaces actually checked; a missing
gitdir; an empty-at-every-level result; a git-disowns-it result carrying the owning
repository path; a contains-a-checkout result carrying the entry count; a
referenced-by-state result carrying the workspace name; a symlink result; and a
state-unreadable result carrying the source file and workspace name. Reference evidence
also identifies the saved repository key and whether the match was by key, exact path, or
ancestor/descendant overlap. Unreadability from any possible referencing file is a global
clearing blocker, never workspace-local permission to remove elsewhere.

Define a `Verdict` enum with exactly three cases: `Live`, `Indeterminate` carrying the
evidence explaining why it could not be cleared, and `Removable` carrying the evidence that
cleared it. `Removable` must carry its proof rather than a bare flag, so plan 05's
re-verification has something concrete to re-derive and compare against, and so the report
a developer reads names the reason rather than asserting a conclusion.

Implement the classification as a single function from an evidence list to a `Verdict`,
with `Indeterminate` as the value returned when no other branch matches — including the
empty-list case. Write it so that adding a new `Evidence` variant later cannot silently
widen the authorization: match exhaustively on blockers first, then require the agreed
clearing set explicitly, then fall through. The predicate implemented here is exactly the
one agreed at the checkpoint in task 1 and nothing more.

Do not include the missing-gitdir signal among the clearing conditions. It is recorded so a
developer reading the report can see it, and it is inert in the decision. Every candidate in
the live dataset satisfies it.

Add the behavior tests above as pure unit tests over the evidence-to-verdict function, with
no filesystem involved. They are the cheapest and most direct statement of the TISO-04
wording, and they must be readable as such by someone auditing the rule later.

  <behavior>
    - Enumeration of a fixture tree shaped like the real one returns one candidate per second-level directory and no others.
    - A second-level directory whose name does not parse as `repository-<u64>` is skipped, including one whose numeric part overflows a `u64`.
    - A candidate that is a symlink is recorded with the symlink signal and is never cleared.
    - A candidate containing entries is recorded with the contains-a-checkout signal and its entry count.
    - A candidate empty at every level is recorded with the empty signal.
    - Running the enumeration over a fixture tree leaves that tree byte-for-byte unchanged — no file created, modified, or removed.

  <action>
Implement `ScanRoots { worktrees_base: PathBuf, config_dir: PathBuf }` and
`scan_at(&ScanRoots)` so all filesystem tests pass both synthetic roots explicitly. The
production `scan()` wrapper derives those roots from `git::real_worktrees_base()` and
`persist::config_dir()`; fixture tests never call that wrapper or resolve a developer root.
Enumeration receives the worktrees base from `ScanRoots`. The tree is exactly three
levels — base, workspace, `repository-<key>`, optional child — so walk it with
`std::fs::read_dir` at each level rather than a generic recursive walker. A generic walker
would weaken the shape check, which is the first filter and the only one that bounds how
much of the filesystem this tool ever looks at.

Canonicalize the real base once, up front, and refuse any candidate whose resolved path
does not remain under it. Parse the key with `str::parse::<u64>()` and treat a parse failure
— including numeric overflow — as a shape mismatch to skip, not as an error to report.

Use the non-following metadata call for every classification decision. The following
variant, and the plain existence check, both traverse symlinks: a symlinked candidate
pointing outside the base would be classified on the target's properties while a later
removal acted on the link, which is how a deletion escapes the base entirely. Record the
symlink signal for any candidate that is itself a link, and treat it as a hard blocker. This
mirrors the refusal already present on the verified-removal path.

Where a candidate does contain a gitdir, run `discover_repository` and the porcelain
worktree listing to determine whether git still registers the path, and record the
git-disowns-it signal only when the lookup succeeded and the path was genuinely absent from
the inventory. A failed lookup is not a disownment — record nothing and let the candidate
stay `Indeterminate`. Widen `parse_worktree_porcelain`, `discover_repository`, and
`persist::load_named_at` to `pub(crate)` as needed; do not add them to the crate's public
API. `load_named_at(root, file)` performs a strict non-locking read. Do not use
`load_for_workspace_strict_at` for scanning: it calls `hold_state_lock`, which creates or
opens a lock and violates scan's no-write contract. Unsupported legacy schemas remain
unreadable blockers rather than triggering migration. Plan 05 reads every state file
independently, including a legacy-named file when a suffixed one also exists.

The enumeration performs no writes of any kind. No temporary files, no lock acquisition, no
directory creation, not even to probe writability. `scan` is a read of the developer's real
data root and its only output is a report (D-16).

Write the filesystem tests against a fixture tree built under a unique temp root, following
the `GitFixture` convention — an atomic counter for the root name and a `Drop` that cleans
up and swallows its errors. Include the byte-for-byte-unchanged assertion by capturing the
tree's entries and modification times before and after the scan.

Note for the summary: the empty-parent leak that produced 1286 of these directories is a
live production defect, not a historical one. `ensure_default_worktree` and
`activate_branch_with_post_add_hook` each create the `repository-<key>` parent before
invoking git and nothing removes it when the subsequent step fails, and no code anywhere
removes an empty parent. Fixing it is **out of scope for this phase** and is recorded as a
v2.2 follow-up. The consequence that matters here: this scanner will keep finding new
candidates after the phase ships, so "zero candidates" must never be treated as an exit
criterion for anything.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scanner -> developer's real data root | The only code in this codebase that deliberately reads the real `~/.local/share/baude/worktrees`, containing both leaked directories and live managed worktrees |
| filesystem metadata -> ownership conclusion | Directory names and link targets are attacker- or accident-controlled inputs to a decision that later authorizes deletion |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-12 | Tampering | `Verdict::Removable` derived from weak evidence | critical | mitigate | Three-way verdict with `Indeterminate` as the default; shape and missing-gitdir explicitly excluded from the clearing set; predicate agreed at a blocking decision checkpoint before implementation (tasks 1, 2) |
| T-08-04 | Tampering | symlinked candidate | high | mitigate | Non-following metadata for every classification; symlink is a hard blocker; canonicalized base with a containment refusal (task 3) |
| T-08-13 | Denial of Service | `repository-<u64>` key parse overflow or non-numeric name | low | mitigate | `str::parse::<u64>()` returns an error on overflow; treated as a shape mismatch and skipped, never as a scan failure (task 3) |
| T-08-14 | Tampering | scan writing to the real data root | high | mitigate | Enumeration performs no writes at all — no temp files, no locks, no probe directories — asserted by a before/after tree comparison (task 3) |
| T-08-15 | Repudiation | a verdict with no recorded reason | medium | mitigate | `Removable` and `Indeterminate` both carry their evidence, so every reported conclusion names what produced it (task 2) |
