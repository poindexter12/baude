  <name>vt100 fork kitty keyboard-mode tracking</name>
  <files>vendor/vt100/src/screen.rs, vendor/vt100/tests/kitty_keyboard.rs</files>
  <behavior>
    Cases (bytes fed via Parser::process → expected screen().kitty_keyboard()):
    - fresh parser → 0
    - b"\x1b[>1u" → 1 (push flags 1)
    - b"\x1b[>1u\x1b[<1u" → 0 (push then pop returns to inactive)
    - b"\x1b[>1u\x1b[>5u" → 5 (nested push; current = top of stack)
    - b"\x1b[>1u\x1b[>5u\x1b[<1u" → 1 (pop one level restores prior)
    - b"\x1b[<99999u" on a fresh parser → 0, no panic (saturating pop of empty/short stack)
    - 40 consecutive pushes → depth capped at 32 (spec cap), no unbounded growth; kitty_keyboard() still reports the most recent flags value
    - b"\x1b[=2;1u" → 2 (set current flags; when the stack is empty, set establishes the active entry)
    - b"\x1b[>1u\x1b[=4;2u" → current flags gain bit 4 (mode 2 = OR given bits); b"...\x1b[=4;3u" clears them (mode 3 = AND NOT)
    - b"\x1b[?u" → 0 and NO bytes are queued in reply — the query probe stays dropped (assert state unchanged; the fork has no reply channel and must not gain one)
    - unrelated CSI with the same intermediates but a different final (e.g. b"\x1b[>0c") → 0, still routed to the existing debug-log fallthrough
  </behavior>
