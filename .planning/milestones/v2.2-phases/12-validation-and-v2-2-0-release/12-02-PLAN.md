    Per **D-05**, add a workspace-lock recovery section. Place it at the end of `## Workspaces`, immediately before `## opencode backend`, since it is the failure mode of the single-writer guarantee that section already describes. This is the one SHIP-02 item no prior phase wrote, and the behavior has been live in released binaries since v2.1.2 with no documentation at all.

    The section must carry:
    - **The exact message a user will see and search for.** Quote the diagnostic from `baude/src/main.rs:377-395` verbatim, both forms — the one naming a pid and the anonymous one — plus the suggestion line and the printed lock path. A user pastes this string into a search box; paraphrasing it makes the section unfindable.
    - **Where the lock lives and how the name is derived.** For a workspace named `claude`, the path is `~/.config/baude/.state-claude.json.lock` — a dotted sibling of the `~/.config/baude/state-<workspace>.json` file the README already names at line 62. Give the general form alongside the worked example.
    - **What the pid means, and what its absence means.** The holder pid is stamped best effort *after* the lock is won. An absent pid does not mean the lock is stale — it means the stamp failed or predates pid stamping, and the lock is still genuinely held.
    - **The safety fact.** This is an OS advisory lock held on an open file descriptor, not a pid-file sentinel. The kernel releases it when the holding process exits, so a crashed baude never wedges a workspace. State plainly: **never delete the lock file.** Removing it while another baude is running does not release that process's lock — it lets a second baude create a fresh file and win, producing two writers on one state file, which is the exact corruption the single-writer design exists to prevent. Do not include any command that removes the lock path; the acceptance gate checks for one.
    - **The recovery steps, in order.** Read the pid from the message and identify the other baude with `ps -p <pid>`. Quit it normally (`ctrl+q` then `q`), or signal it if it is wedged. Or sidestep entirely with `BAUDE_WORKSPACE=<name> baude`, which the diagnostic itself already suggests. If the message shows no pid, find the holder with `lsof` against the lock path.
    - A one-line note that the daemon surfaces the same diagnostic.
  </action>
