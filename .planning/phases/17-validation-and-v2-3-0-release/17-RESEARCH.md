## Phases 13-16 Deliverables to Validate

### Phase 13: Workspace Derivation and New-Session Open Defaults

**Delivered features:**
- Baude opened from a folder derives its workspace/namespace from the folder's git repository root name instead of colliding across folders
- `new-session` and `open` default to the launch folder instead of hardcoded defaults
- Folder breadcrumbs persist the sessions actually used from each folder

**README sections covering this:**
- "Folder context" (ancestor walk, breadcrumbs, workspace binding, derivation rules)
- "Workspaces" (precedence order, when derivation applies, examples)
- "Configuration" (new_session_dir, folder_context keys)

**Smoke test verification:**
1. Launch baude from `~/Code/github.com/owner/repo/src` (subfolder of a git repo)
2. Check status bar: workspace name should be derived from the repo root folder name (e.g., `baude` from a repo named `baude`), not the default `claude`
3. Check breadcrumbs: `~/.config/baude/breadcrumbs-<workspace>.json` exists and references the sessions from this folder
4. Create a new session with `n`: the prompt should default to the launch folder, not `~/Code/github.com`

### Phase 14: Managed Worktree Identity

**Delivered features:**
- Managed repository directories use a 12-hex SHA-256 digest keyed on the git common directory
- Format: `repository-<12 hex digits>/<role>-<checkout_key>`
- Legacy counter-based directories (`repository-1/`, `repository-2/`) still resolve but are not created for new repos
- `.baude-marker.json` file inside each directory records and verifies ownership
- Collision detection: if two repositories converge on same path, allocator adds non-destructive suffix (`repository-<12hex>-2`, etc.)

**README sections covering this:**
- "Worktrees" (digest scheme, marker file, legacy support, collision detection)

**Smoke test verification:**
1. Create a managed worktree with `w`: verify the path under `~/.local/share/baude/worktrees/` uses the digest format (e.g., `repository-a1b2c3d4e5f6/`)
2. Run `baude worktrees scan --json` and verify digest-based paths, not counter-based ones
3. Verify `.baude-marker.json` exists in the worktree directory with repo ownership metadata
4. (Collision test is too hard to trigger manually; rely on code review)

### Phase 15: Startup and Idle Performance

**Delivered features:**
- Dirty-flag render loop: zero terminal writes while idle
- Startup timing with stages: `config_load`, `workspace_resolution`, `keyboard_probe`, `terminal_setup`, `app_new`, `first_frame`, `session_restore`, `first_metadata_poll`, `total`
- First frame painted before session restore
- Two-phase restore: PTY paused at spawn, released one per loop iteration after durable save
- Metadata polling gates: skip archived/exited rows, mtime check on live rows
- Identity-verified suspend/resume via SIGSTOP/SIGCONT before signaling
- `idle_child_policy` (keep/suspend/stop) applied by both TUI and daemon
- Usage poller optional via `usage_poll_secs: 0`
- Static status codes `? B ✓ ✗ - A !` replacing spinner glyphs

**README sections covering this:**
- "Status codes" (static single-character glyphs, per-state colors, one-line legend for tall terminals)
- "Performance" subsections: "Startup Timing" (BAUDE_TIMING=1), "Idle Behavior" (zero writes, polling gates, release one per iteration), "idle_child_policy" (keep/suspend/stop), "usage_poll_secs" (interval, 0 disables)
- "Configuration" (idle_child_policy, usage_poll_secs config keys and env overrides)

**Smoke test verification:**
1. Run `BAUDE_TIMING=1 baude` and verify stderr shows timing stages with `first_frame` before `session_restore`
2. Start a session and observe that the status code is a single character (`?`, `B`, `✓`, etc.), not an animated spinner
3. With a session archived, verify the idle_child_policy is applied:
   - Config `idle_child_policy: suspend` → session shows "suspended" state
   - Config `idle_child_policy: stop` → session shows "✗ exited"
   - Config `idle_child_policy: keep` (default) → session remains in its last state
4. Verify that with no input, baude makes zero terminal writes: run `BAUDE_TIMING=1 baude` and let it sit idle for 30 seconds, then observe that stderr shows single timing lines (no per-second redraws)
5. Verify `usage_poll_secs: 0` disables the usage poller: set config `usage_poll_secs: 0` and observe the footer shows "usage: off"

## Release Mechanism Details

### release-please Workflow (`.github/workflows/release-please.yml`)

**When it runs:**
- On every push to `main` branch
- Uses GitHub App token (RELEASE_PLEASE_APP_ID + RELEASE_PLEASE_APP_PRIVATE_KEY secrets) for permissions

**What it does:**
1. Reads the current version from `.release-please-manifest.json`
2. Scans commit log for conventional commits since last release
3. Determines bump tier (major/minor/patch) based on commit types (breaking → major, feat → minor, fix/others → patch)
4. If a release PR already exists, updates it; otherwise creates a new one
5. Release PR includes:
   - Version bumps in Cargo.toml, baude-core/Cargo.toml, baude/Cargo.toml, bauded/Cargo.toml
   - Updated CHANGELOG.md with entries per commit
   - Updated Cargo.lock
6. Applies a label per tier: `release:patch`, `release:minor`, or `release:major`
7. Auto-merge behavior:
   - **patch:** immediately enabled via `gh pr merge --auto --merge` (merges when all required checks pass)
   - **minor:** no auto-merge; waits for manual review after a "soak" period
   - **major:** no auto-merge; adds comment requesting manual merge

### release.yml Workflow (`.github/workflows/release.yml`)

**When it runs:**
- On `release: published` event (triggered after release-please PR merges and creates the tag)

**What it does:**
1. Checks out the tagged commit
2. Builds multi-arch binaries:
   - aarch64-apple-darwin (macos-14)
   - x86_64-apple-darwin (macos-14)
   - x86_64-unknown-linux-gnu (ubuntu-22.04)
   - aarch64-unknown-linux-gnu (ubuntu-22.04-arm)
3. Builds multi-arch Docker images (linux/amd64, linux/arm64) on ghcr.io
4. Attaches binary tarballs and SHA256SUMS to the GitHub Release

### Version Bumping in release-please-config.json

**release-type:** `simple` — uses a single version string for the whole repo

**extra-files:** Updated by release-please when the release PR is created:
- `Cargo.toml` (root workspace) — uses pattern `version = "X.Y.Z"` in `[workspace.dependencies]`
- `baude-core/Cargo.toml` — updates `[package]` version
- `baude/Cargo.toml` — updates `[package]` version
- `bauded/Cargo.toml` — updates `[package]` version

**Manifest file:** `.release-please-manifest.json` tracks the current released version

## Orchestrator addendum (2026-09-22): repository merge rules, checked live

```
gh api repos/poindexter12/baude --jq '{squash,merge,rebase,default}'
  -> {"default":"main","merge":true,"rebase":true,"squash":true}
gh api repos/poindexter12/baude/branches/main/protection
  -> required_linear_history.enabled = false
     required_pull_request_reviews  = null
     required_status_checks.contexts = ["check (macos-14)", "check (ubuntu-22.04)", "docker"]
```

Consequences for this phase:

- **Merge, do not rebase.** Linear history is not required and merge commits are allowed, so
  replaying ~194 commits buys nothing and costs repeated conflict resolution on the same version
  metadata. Task 4 was rewritten accordingly.
- **No required reviewers**, so nothing external gates the pull request except the three status
  checks above. That makes it MORE important, not less, that all four local gates are green before
  anything is pushed.
- **Pushing and opening the pull request are outward-facing** and are deliberately excluded from the
  automated tasks; the repository owner authorizes them.
