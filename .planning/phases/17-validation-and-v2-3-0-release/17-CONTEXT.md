# Phase 17 Context: Validation and v2.3.0 Release

**Objective:** Validate that v2.3.0 is stable and ready for release, then prepare the release-please PR for merging by a maintainer.

**Phase scope:** Validation (cargo test, cargo clippy, cargo build, cargo fmt), manual terminal smoke test confirming phases 13-16 work end-to-end, verification that README and release notes reflect the delivered features, and integrating origin/main (by merge) before the release pull request is opened.

---

## Critical Decisions

**1. Does the branch rebase onto origin/main happen inside this phase, and if so does it come before or after the validation gates run?**

Integration happens AFTER the validation gates, and it is a MERGE, not a rebase. The branch is ~194 commits ahead of origin/main and 2 behind (the v2.2.0 release commit and the merge of the previous release PR). Checked against the live repository on 2026-09-22: `required_linear_history` is **false** on `main` and `allow_merge_commit` is **true**, so nothing forces a replay. Rebasing would mint ~194 new SHAs and re-resolve the same version-number conflict repeatedly; merging resolves it once and keeps every reviewed SHA intact. Order: validate on the current branch, then merge origin/main, then re-run all four gates on the merged tree. A `backup/pre-main-merge-*` ref is taken before the merge, and a conflict outside version/changelog metadata stops the task for a human.

---

**2. Where do the release notes live: a hand-written section in CHANGELOG.md, the release-please generated entry, or the PR body?**

Release notes are generated by release-please from the commit log and written to CHANGELOG.md when the release PR merges. There is no hand-written section; release-please uses conventional commit messages (feat, fix, docs scopes) to auto-generate the changelog. The ROADMAP success criteria "Release notes and README reflect the new defaults" means we must verify the generated changelog accurately describes the delivered phases (13: workspace derivation + new-session defaults, 14: worktree identity scheme, 15: startup performance + idle behavior, 16: pane focus UX) and update the README to document phase 16's new keybinding if phase 16 has not yet completed at time of Phase 17.

**3. What exactly is in the manual smoke checklist versus the automated one.**

**Automated (scripted, non-interactive):**
- `cargo test --workspace` (787 tests as of phase 15 completion)
- `cargo clippy --all-targets -- -D warnings`
- `cargo build --workspace`
- `cargo fmt --all -- --check`

**Manual (human at terminal, ordered checklist with exact expected observations):**
1. Launch baude from a git repository subfolder (no prior binding) and verify workspace is derived from the repository root folder name (check the status bar shows the derived workspace name, not "claude").
2. Create a new session with `n` from a folder that hasn't been launched before, confirm it defaults to the working directory or the configured `new_session_dir` (not a hardcoded fallback).
3. Open a session, observe the startup timing output with `BAUDE_TIMING=1 baude` and verify "first_frame" comes before "session_restore" in the stderr output.
4. Verify `baude worktrees scan --json` shows the 12-hex SHA-256 digest-based directory names (e.g., `repository-abc123def456/`) for managed worktrees, not counter-based names (e.g., `repository-1/`).
5. Verify pane focus behavior: start a session with shell pane open, press `alt+↑/↓` and confirm focus toggles between Claude and shell panes (if phase 16 is complete).
6. With an open session, archive it with `a` and observe that the idle_child_policy is applied: if the config has `suspend`, the session shows "suspended" state; if `stop`, it shows "✗ exited"; if `keep` (default), it remains "waiting".
7. Observe that the status line shows a one-character status code per session (`?`, `B`, `✓`, `✗`, `-`, `A`, `!`) instead of animated spinners.

The phase ends at "release-please PR is opened, green (all checks pass), and ready for a maintainer to merge." ## Release Mechanism

**release-please workflow** (`.github/workflows/release-please.yml`):
- Triggered on push to main; maintains a single open release PR with version bumps + Cargo.lock + CHANGELOG.md
- Classification: patch (auto-merge), minor (soak, label only), major (manual merge + comment)
- Determines bump tier by comparing old/new version in release-please-manifest.json
- Uses GitHub App token (RELEASE_PLEASE_APP_ID + RELEASE_PLEASE_APP_PRIVATE_KEY) for permissions

**release.yml workflow** (`.github/workflows/release.yml`):
- Triggered on `release: published` event (not tag push)
- Builds multi-arch binaries (aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu)
- Builds multi-arch Docker images (linux/amd64, linux/arm64) on ghcr.io
- Attaches tarballs and checksums to the GitHub Release

**release-please-config.json**:
- release-type: simple
- changelog-path: CHANGELOG.md
- extra-files: Cargo.toml (workspace), baude-core/Cargo.toml, baude/Cargo.toml, bauded/Cargo.toml
- No component-in-tag (tags are vX.Y.Z, not v<component>-X.Y.Z)

**Commit scopes in this repo:** feat(), fix(), test(), docs(), chore(), style(), fmt()
- Phase tags: feat(17), test(17), docs(17), etc.
