<research_deviations>
Two locked decisions are implemented by a different mechanism than CONTEXT.md names. Both
corrections come from falsification probes run in this environment (RESEARCH Findings 1
and 2), and both are stated here rather than applied silently.

**Deviation 1 — D-09 / D-12: `#[cfg(test)]` cannot arm a downstream test binary.**
CONTEXT.md locks "armed unconditionally under `#[cfg(test)]` … `#[cfg(test)]`-only
compilation." The `test` cfg is set per crate by `rustc --test`. When cargo builds
`baude`'s test harness, `baude-core` is compiled as an ordinary library with `test` false.
A `#[cfg(test)]`-only guard in `baude-core` would therefore be **absent from `baude`'s and
`bauded`'s test binaries** — the two binaries whose fixtures produced the leak. The probe
output is in RESEARCH Finding 1 (`cfg_test_in_dep=false` inside the downstream test run).

The intent of D-09 and D-12 is preserved exactly by `cfg(any(test, feature =
"test-support"))` with the feature enabled from `[dev-dependencies]`: `test` covers
`baude-core`'s own harness, the feature covers the two downstream harnesses, and the same
probe confirms the feature is off in both `cargo run` and `cargo run --release`. Task 1's
verify measures the production-cost half of D-12 directly rather than assuming it.

**Deviation 2 — D-01's stated rationale is refuted; the guard is still correct.**
CONTEXT.md justifies the RAII guard with "arming leaks across tests within a binary."
That is true of the process-wide `AtomicBool`, but false of the thread-locals: libtest
allocates a fresh thread per `#[test]` even under `--test-threads=1` (the command CI runs),
so a thread-local override never reaches the next test. The guard is still built — it gives
nested scoping and it lets the arming flag be deleted — but this plan deliberately writes
**no** test of the form "an override set by test A is invisible to test B." That assertion
passes on today's unchanged code and would certify nothing (RESEARCH Pitfall 4). Task 3
verifies the property that actually fails today instead: an unguarded resolution in a test
binary aborts the test.
</research_deviations>

that distinction is load-bearing in two directions. It satisfies D-09 without any arming
state at all — the guard becomes a property of the compiled binary rather than of execution
history, so it holds for the first test in a binary as much as the thousandth. And it lets
the re-exec'd dogfood child pass: that child is the same test binary re-invoked with
`--exact`, isolated by `HOME`/`XDG_DATA_HOME` rather than by thread-locals, so every real
path it resolves already lands inside `BAUDE_TEST_FIXTURE_ROOT`. That resolves D-17 —
`BAUDE_TEST_FIXTURE_ROOT` is sufficient, provided the guard checks containment against it
rather than merely noting it is set.

| cargo feature resolution -> shipped binary | The boundary that must keep test-support code out of release artifacts |
