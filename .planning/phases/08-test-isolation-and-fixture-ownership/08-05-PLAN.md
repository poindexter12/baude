<research_deviations>
**State is the ownership-negative evidence source, inverting CONTEXT.md's reasoning.**
CONTEXT.md dismisses state because it "has zero record of the leaked directories." That
silence is the point: `SavedCheckout` records `observed_path`, so a directory state *does*
reference is definitively live and must never be a candidate. Two directories in the live
dataset — `claude/repository-1` and `claude/repository-5` — match the leak shape exactly,
were created by production after the v2.1.4 fix landed, and correspond to real repositories
in `state-claude.json`. Without the state cross-reference they are indistinguishable from
the 1431 genuine leaks.

The cross-reference must cover **every** workspace's state files, not only the active one.
The naming is `state-<workspace>.json` and `daemon-state-<workspace>.json`, plus the legacy
unsuffixed `state.json` and `daemon-state.json` which belong to the default `claude`
workspace. The developer's real config directory holds all eight of these today. Missing
one file class silently converts "not referenced" into "not checked."
</research_deviations>

    - A candidate referenced only by a non-default workspace's state is still reported Live — the cross-reference is not limited to the active workspace.
    - A candidate referenced only by a legacy unsuffixed state file is still reported Live.
    - A candidate referenced only by a daemon state file is still reported Live.
    - When one workspace's state file exists but cannot be parsed, every candidate in that workspace resolves to Indeterminate, and candidates in other workspaces are unaffected.

  <action>
Implement the state cross-reference as the ownership-negative evidence source. Enumerate
every workspace present under the real base, and for each one read the full set of state
filenames: the suffixed `state-<workspace>.json` and `daemon-state-<workspace>.json`, plus
the legacy unsuffixed pair for the default workspace. Derive those names from
`workspace::state_file` and `legacy_state_file` rather than formatting strings locally, so
a future rename cannot leave this module reading a filename that no longer exists.

For each state file that parses, collect every `SavedCheckout.observed_path` and test each
candidate against the set. A candidate that matches records the referenced-by-state signal
naming the workspace, and becomes a hard blocker. A candidate that matches nothing, in a
run where every state file parsed successfully, records the not-referenced-by-state signal
carrying the list of workspaces actually checked — the list is what makes the claim
auditable later.

Distinguish three outcomes per state file and do not collapse them: parsed successfully,
absent entirely, and present but unreadable or unparseable. Absent is a legitimate
successfully-checked absence. Unreadable is not: record the state-unreadable signal for that
workspace and let it block every candidate in it. Deriving "not referenced" from a file you
could not read is inferring an absence from a failure, and it is the exact mistake that
would have cleared the two live production directories. This matches the fail-closed
precedent already set by `inspect_removal`.

Compare paths after canonicalizing both sides against the same base, so a trailing separator
or a relative segment in a persisted path cannot cause a live directory to miss its match.
A canonicalization failure on either side is an unreadable outcome, not a mismatch.
  </action>

<task type="checkpoint:decision" gate="blocking">
  <decision>Confirm the prune execution semantics before writing the first code in this phase that deletes data</decision>
  <context>
Plan 04's checkpoint settled *which evidence* clears a candidate. This one settles *what
happens when a developer acts on that report*, and it is a separate one-way door: task 2 is
the first code in Phase 8 that removes a directory under the developer's real data root, and
no revert recovers what it deletes.

The proposed semantics, all four together:

1. Prune re-derives every evidence item from scratch — shape, filesystem classification,
   state cross-reference, git inventory — rather than trusting the scan's recorded verdict.
2. The re-derived proof must *match* the proof recorded at scan time. A candidate that newly
   qualifies between scan and prune is refused as firmly as one that stopped qualifying, on
   the grounds that the developer approved a specific reported set rather than a predicate.
3. Removal requires the prune flag *and* a separate explicit confirmation flag. Prune without
   confirmation runs the full re-verification and reports, removing nothing.
4. Candidates that still contain a gitdir are removed through the existing verified-removal
   path and its `inspect_removal` analysis, not by direct directory removal.

The live context: 1433 candidates exist under the real root right now, 1286 of them empty,
and two directories matching the same shape hold real checkouts for repositories the
developer actively uses.
  </context>
  <options>
    <option id="all-four">
      <name>Approve all four semantics as proposed</name>
      <pros>Every known failure mode between reading a report and acting on it is closed; the default path still removes nothing</pros>
      <cons>A developer who scans, then legitimately creates a new leak, must re-scan before pruning it</cons>
    </option>
    <option id="drop-proof-match">
      <name>Approve without clause 2 — re-derive, but accept any candidate that re-derives as `Removable`</name>
      <pros>Fewer surprising refusals; a stale report is still safe because re-derivation is full</pros>
      <cons>Prune acts on candidates the developer never saw in a report, which makes the approval a predicate approval rather than a set approval</cons>
    </option>
    <option id="interactive">
      <name>Approve all four, plus require per-candidate interactive confirmation rather than one flag</name>
      <pros>Nothing is removed without the developer seeing that specific path at the moment of removal</pros>
      <cons>Unusable against a 1433-entry dataset, and the phase's stated CLI shape is scriptable and headless</cons>
    </option>
  </options>
  <resume-signal>Reply with the option id (`all-four`, `drop-proof-match`, `interactive`), or state different semantics. Task 2 does not begin until one is chosen.</resume-signal>

    - A candidate that was Removable at scan time but acquires a blocker before prune runs is refused, and the refusal names the blocker.
    - A candidate whose re-derived evidence no longer matches the evidence recorded at scan time is refused.
    - A candidate that is Indeterminate or Live at re-verification is refused.

    - Prune invoked without explicit confirmation removes nothing and reports what it would have done.
  </behavior>
  <action>
Implement the prune entry point as a function that takes the previously reported candidates
and, for each one, re-derives every evidence item from scratch — the shape check, the
filesystem classification, the state cross-reference, and the git inventory lookup — before
removing anything. Re-derivation is the mitigation for the gap between the developer reading
a report and acting on it: the state file may have changed, git may have re-registered the
path, or the directory may have been replaced by a link. The recorded evidence from the scan
is used only as a comparison, never as the authorization (D-15).

Require the re-derived verdict to be `Removable` *and* its proof to match the proof recorded
at scan time. A candidate that newly qualifies between scan and prune is refused just as
firmly as one that stopped qualifying — the developer approved a specific reported set, not
a predicate.

Where a candidate still contains a gitdir, route the removal through the existing
verified-removal path and its `inspect_removal` analysis rather than removing the directory
directly, so this code inherits the fail-closed semantics already established there. Re-check
the non-following metadata immediately before the removal call itself, not merely at the top
of the re-derivation, and refuse on any link.

Take confirmation as an explicit parameter with no default that removes. Without it, prune
runs the full re-verification and reports the outcome, removing nothing — that is the
preview-only default the project constraint requires (D-16), and it also gives a developer a
way to see the re-verification result before committing to it.

Return a per-candidate outcome record for every candidate, including the refused ones and the
reason for each refusal, so the caller can print a complete account rather than only the
successes.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI operator -> real data root deletion | The only interface in this codebase that can remove directories under the developer's real data root |
| persisted state file -> ownership conclusion | A state file is an untrusted input to the decision: it may be absent, stale, truncated by an interrupted atomic write, or unparseable |
| scan report -> prune action | Time passes between the report a developer reads and the removal they approve; conditions can change in that window |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-16 | Tampering | unreadable state read as "not referenced" | critical | mitigate | Three-way per-file outcome; unreadable blocks every candidate in that workspace and can never contribute to clearing (task 1) |
| T-08-05 | Tampering | TOCTOU between scan and prune | high | mitigate | Every evidence item re-derived from scratch at removal time, with the re-derived proof required to match the approved one (task 2) |
| T-08-04 | Tampering | candidate replaced by a symlink before removal | high | mitigate | Non-following metadata re-checked immediately before the removal call, not only at the top of re-derivation; symlink refused (task 2) |
| T-08-17 | Elevation of Privilege | destructive verb reachable from the headless daemon | high | mitigate | The arm is added to `baude` only; `bauded` has no operator to approve and gets no corresponding verb (task 3) |
| T-08-18 | Tampering | single-flag accidental deletion | high | mitigate | Two distinct opt-in flags required on one command line; neither alone removes anything (tasks 2, 3) |
| T-08-15 | Repudiation | removals with no account of what was refused and why | medium | mitigate | Per-candidate outcome record covering refusals and their reasons, surfaced in both the grouped summary and the JSON output (tasks 2, 3) |
| T-08-19 | Information Disclosure | JSON output containing repository paths | low | accept | The output describes the developer's own local tree on their own machine and is printed to their own terminal; no transmission surface exists |
</threat_model>
