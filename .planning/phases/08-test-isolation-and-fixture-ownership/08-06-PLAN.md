<objective>
Make the isolation guarantee observable at the level the phase goal states it — a whole
suite run, not a single resolver — and remove the copied fixture preamble that made the
original leak easy to reintroduce.

Purpose: plans 01 through 03 each prove one resolver is contained. The phase goal is that
*running the suite* cannot read or write the developer's real config, state, or `~/.claude`.
Nothing asserts that today, and no mechanism exists to assert it. Meanwhile the same
twelve-line fixture preamble appears ten times in `bauded/src/manager.rs`; a contributor
adding an eleventh copy is how a guard gets omitted.

Output: a shared `bauded` fixture helper, and a scripted real-root assertion wired into CI
around the full suite.
</objective>

<interface_from_prior_plan>
From plan 01, in `baude_core::testing` behind `cfg(any(test, feature = "test-support"))`:
`TestRedirect::new(root)`, `#[must_use]`, reverting on drop, covering the config dir, the
state dir, the managed worktrees root, and the hook command at once; and
`persist::release_state_lock_for_test`, now `pub` and reachable from `bauded`.

From plan 03, `workspace::override_for_test(&Config, hint) -> TestRedirect` establishes a
literal identity in the same redirect storage. `active()` is reader-only and panics in
support builds without this override even if `ACTIVE` is populated. `initialize(&config,
hint)` in a support build updates only an already-held fixture scope, never the production
cache; the helper must establish that scope before any manager/backend reader.

From plan 08, App usage/ambient remote workers are inert in test builds, UI ownership
regressions have executed, and Pty::spawn_registered_with requires contained config/Claude
roots before child creation. All manager tests that launch a session or shell therefore
need ManagerFixture even if persist=false and no metadata polling occurs. Child environment
containment comes from the core launcher, not from thread-local propagation into a shell.

`bauded/Cargo.toml` already carries `baude-core = { workspace = true, features =
["test-support"] }` under `[dev-dependencies]` from plan 01.

Plan 01 also deleted `git::set_worktrees_base_for_test` and converted its twelve call sites,
including all ten `manager.rs` preambles, each of which now binds a `TestRedirect` to a named
local. Those bindings are what this plan's helper absorbs into a field.

`bauded` is a binary-only crate: its test target is selected with `cargo test -p bauded
--bins`, never `--lib` (plan 01 `<crate_shape>`). No verify command pipes a gate into another
command, because a pipeline reports the last stage's exit status and masks failure — task 2's
verify captures each status into its own variable for exactly that reason.

    - Constructing the helper yields a fixture whose root is unique within the process, with the redirect guard held for the fixture's lifetime.
    - Two helpers constructed in the same test have different roots.
    - Dropping the helper reverts the redirect and cleans up its root, swallowing cleanup errors.
    - Every existing `manager` test passes with its preamble replaced by a helper construction.
  </behavior>
  <action>
Diff all ten preamble copies against each other before writing the helper. They are reported
to differ only in a label string, but that is an assumption rather than a verified fact —
some may set up more than the preamble, and folding a divergent one into a shared helper
would silently change what its test exercises. Where a copy does more, leave that extra setup
at the call site rather than widening the helper to accommodate it.

Build a `ManagerFixture` type following the `GitFixture` convention already in the codebase:
an atomic counter producing a process-unique root name, construction that creates the root
and takes the label, and a `Drop` that cleans up and swallows its errors the way the existing
fixture does.

The helper must **hold** the redirect guard as a field rather than constructing one and
letting it drop. An unbound guard arms and disarms in the same statement, and a fixture built
that way runs entirely unredirected while appearing correct — the single most likely way to
reintroduce the leak this phase exists to close. Storing it as a field ties the redirect's
lifetime to the fixture's, which is the whole reason the guard is RAII (D-01). Take the
identity override the same way, using a literal config that explicitly chooses the
scenario's workspace/backend. Declare or explicitly drop the identity guard before the root
guard so nested restoration unwinds in reverse construction order. One construction
establishes root, redirects and workspace identity together (D-04, D-05, D-08, D-18).
Audit remaining Manager tests with ambient backend/identity/config readers or any PTY
creation/restart/open-shell path and use the helper there too, including persist=false
cases, before Manager construction or restore. Hold it until worker/PTY teardown, not
only until create returns. A test without an identity override must panic, never reuse
another fixture's process cache.

Replace each preamble one at a time, retaining all scenario-specific setup and custom
commands. Name helper ownership/identity tests with the `fixture_isolation_` prefix and
run that narrow group during migration. Only after every manager consumer is migrated and
plans 01/02/03/08 are complete may task 2 run full binaries or the suite.

The helper is downstream test code, so place it in `manager.rs`'s existing `#[cfg(test)]`
module, not behind a `test-support` predicate belonging to `baude-core`. No downstream
feature of that name is declared or needed.
  </action>

  </verify>

<task type="auto">
  <name>Task 2: Assert a full suite run leaves the real config, `~/.claude`, and worktrees root untouched</name>
  <files>scripts/assert-real-roots-untouched.sh, .github/workflows/ci.yml</files>
  <read_first>
    - `.github/workflows/ci.yml:17-24` — the existing `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test -- --test-threads=1` steps, and the matrix of runners they execute on.
  </read_first>
  <precondition>CI runners provide a writable HOME; the script must operate on whatever real roots resolve on the runner rather than assuming the developer's paths exist.</precondition>
  <action>
Write `scripts/assert-real-roots-untouched.sh` as the suite-level statement of the phase goal.
It takes a mode argument: a "before" mode that records a fingerprint of the three real roots,
and an "after" mode that recomputes the fingerprint and exits non-zero if anything changed.

Fingerprint the same roots the app resolves, with these distinct precedence chains:

| Root | Exact resolver precedence |
|------|---------------------------|
| config and state (also push/VAPID) | present XDG_CONFIG_HOME, else dirs::home_dir()/.config, else `.`, then append `baude` |
| Claude config | present CLAUDE_CONFIG_DIR, else dirs::home_dir()/.claude, else `.`; never consult XDG_CONFIG_HOME and never append `baude` |
| managed worktrees | present XDG_DATA_HOME, else dirs::home_dir()/.local/share, else `/tmp`, then append `baude/worktrees` |

Mirror `var_os` presence, including empty values, rather than shell nonempty/default
substitution. On supported Unix runners `dirs::home_dir` uses nonempty HOME and then the
passwd home fallback; it is not simply a shell HOME expansion. Use Python 3's standard
library from the shell script for lossless paths, pwd fallback, sorting and hashing; no
package install is needed. Record normalized resolved root paths with the before snapshot;
a different after-resolution is itself a failure. Store snapshots outside all observed
roots in a unique caller-owned temporary directory (CI RUNNER_TEMP or the session scratch
location), never inside config/state/worktrees.

Implement a `--self-test` mode in this same script. It creates only synthetic directories
and launches subprocesses with explicit child env maps; it never changes the parent env or
observes developer roots. Table-test all three chains with distinct HOME, XDG_CONFIG_HOME,
XDG_DATA_HOME, CLAUDE_CONFIG_DIR sentinels. Cover Claude's override winning over HOME/XDG,
HOME fallback, empty/present override values, injected passwd-home fallback, and no-home
terminal fallbacks through the same pure resolver helper used by before/after. Supply
home-lookup inputs to that helper in self-tests rather than querying a real account root.
Also exercise unchanged, newly created, modified and missing roots with synthetic trees;
intentional mutations for falsification happen only inside those trees.

Record, per root, a sorted listing of entries with their sizes and modification times,
and hash it. Treat a root that
does not exist as a distinct recorded state, not as an error — CI runners will not have
them — and treat "did not exist before and does not exist after" as a pass while "did not
exist before but exists after" is a failure. A test run that *creates* one of these
directories is exactly the leak this phase closes.

Make the failure output name which root changed and print the differing entries, not just a
hash mismatch. A bare hash comparison tells a developer that something leaked but not what,
and the diagnostic is the part that gets used.

Capture the exit status of the comparison directly and let it propagate. Do not pipe the
comparison into another command and read the status afterwards — that reports the status of
the last command in the pipeline and masks the real failure.

Wire it into `.github/workflows/ci.yml` as a step immediately before the existing full-suite
step and another immediately after it, with the "after" step configured to run even if the
suite itself failed. A suite that fails *and* leaks is the case most worth catching, and a
step that only runs on success would miss it.

Run the script's synthetic self-tests first. This task is the first broad-test boundary:
plans 01/02/03/08 and task 1 must be complete, including app/API/UI/core/manager guard
lifetimes, explicit identities, both config resolvers, push storage, inert usage/ambient
remote workers, test PTY child environment and dogfood child environment. Re-run the
worker_isolation_app_, worker_isolation_pty_ and ui_fixture_isolation_ filters before
observing any real root. Then run before / full serial suite / after and record independent
statuses. The serial
suite includes the dogfood and second-install hook reconciliation regressions deferred by
plans 01-03. Also run both full downstream binaries without a serial flag, bracketed by
before/after, to prove concurrency does not change containment. Run clippy, formatting and
release compilation as integration gates, not as sub-20-second task checks. Fail rather
than weaken guards if an unmigrated consumer surfaces.

The observer is external to the test process. Its no-write measurement does not by itself
prove absence of reads; resolver panics, explicit literal identity tests, retained UI
ownership, and plan 08's synthetic worker/PTY no-inheritance regressions establish that
part of the goal. Record those separately from no-write evidence. This is future execution
work; a planning-only revision must not invoke the observer or run tests.
  </action>

    <fails_when>The synthetic resolver/worker/PTY/UI controls fail or a named regression is absent, before-snapshot fails, the full suite exits nonzero, or after detects a changed/resolved-differently root or cannot compare snapshots. Suite and observer statuses are captured independently; either fails the gate. This is a 4-6 minute warm integration gate, not a fast filter.</fails_when>
  </verify>
  <acceptance_criteria>
    - The script exits zero across a full suite run with no change to any of the three real roots.
    - Synthetic self-tests confirm exact per-root resolver precedence, including CLAUDE_CONFIG_DIR over HOME and no Claude XDG lookup.
    - Deliberately mutating only a synthetic root between the two invocations makes the script exit non-zero and name that root; never touch developer files for falsification.
    - A root that is absent before and after is a pass; a root created during the run is a failure.
    - CI runs the "after" step even when the suite step fails.
    - The full-suite result and the assertion result are reported independently, neither masking the other.
  </acceptance_criteria>
  <done>The phase goal is asserted at suite level by a check that fails when the suite touches a real root.</done>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| full suite run -> developer's three real roots | The aggregate boundary the phase goal names; individual resolver guards constrain it but nothing observes it as a whole |
| new fixture written by a future contributor -> redirect guard | A fixture that omits or mis-binds the guard writes to the real roots exactly as the original leak did |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-20 | Information Disclosure | suite-level writes to the real roots | high | mitigate | Fingerprint-before / compare-after script wired into CI around the full-suite step, running even on suite failure (task 2) |
| T-08-09 | Denial of Service | redirect guard constructed but not held | high | mitigate | The fixture helper stores the guard as a field, tying the redirect to the fixture lifetime; `#[must_use]` plus CI's clippy denial catches the unbound form (task 1) |
| T-08-21 | Tampering | an eleventh copied preamble omitting the guard | medium | mitigate | One construction replaces ten copies, so the guard is established by the helper rather than by each author remembering (task 1) |
| T-08-22 | Repudiation | a leak detected with no indication of what leaked | medium | mitigate | Failure output names the changed root and prints the differing entries rather than reporting a hash mismatch (task 2) |
</threat_model>
