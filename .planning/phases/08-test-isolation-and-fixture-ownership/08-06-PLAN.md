<objective>
Make the isolation guarantee observable at the level the phase goal states it — a whole
suite run, not a single resolver — and remove the copied fixture preamble that made the
original leak easy to reintroduce.

Purpose: plans 01 through 03 each prove one resolver is contained. The phase goal is that
*running the suite* cannot read or write the developer's real config, state, or `~/.claude`.
Nothing asserts that today, and no mechanism exists to assert it. Meanwhile the same
twelve-line fixture preamble appears ten times in `bauded/src/manager.rs`; a contributor
adding an eleventh copy is how a guard gets omitted.

Output: a shared `bauded` fixture helper, and a scripted real-root assertion wired into CI
around the full suite.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: Extract the ten copied `bauded` fixture preambles into one helper</name>
  <files>bauded/src/manager.rs</files>
  <read_first>
    - `bauded/src/manager.rs` at lines 2615, 2698, 2729, 2811, 2843, 2933, 3049, 3136, 3215, and 3521 — all ten preamble copies. Read every one before extracting.
    - `baude-core/src/git.rs:2706-2718` and `:2903` — `GitFixture`, its `AtomicU64` unique-root scheme, and its error-swallowing `Drop`; this helper follows the same convention.
  </read_first>
  <behavior>
    - Constructing the helper yields a fixture whose root is unique within the process, with the redirect guard held for the fixture's lifetime.
    - Two helpers constructed in the same test have different roots.
    - Dropping the helper reverts the redirect and cleans up its root, swallowing cleanup errors.
    - Every existing `manager` test passes with its preamble replaced by a helper construction.
  </behavior>
  <action>
Diff all ten preamble copies against each other before writing the helper. They are reported
to differ only in a label string, but that is an assumption rather than a verified fact —
some may set up more than the preamble, and folding a divergent one into a shared helper
would silently change what its test exercises. Where a copy does more, leave that extra setup
at the call site rather than widening the helper to accommodate it.

Build a `ManagerFixture` type following the `GitFixture` convention already in the codebase:
an atomic counter producing a process-unique root name, construction that creates the root
and takes the label, and a `Drop` that cleans up and swallows its errors the way the existing
fixture does.

The helper must **hold** the redirect guard as a field rather than constructing one and
letting it drop. An unbound guard arms and disarms in the same statement, and a fixture built
that way runs entirely unredirected while appearing correct — the single most likely way to
reintroduce the leak this phase exists to close. Storing it as a field ties the redirect's
lifetime to the fixture's, which is the whole reason the guard is RAII (D-01). Take the
identity override the same way, so one construction establishes root, redirects, and
workspace identity together (D-04).

Replace each of the ten preambles with a helper construction, one at a time, running that
test's own module after each replacement rather than all ten at the end. A behavior change in
the seventh copy is much cheaper to find that way.

Expose the helper under the same `cfg(any(test, feature = "test-support"))` predicate used
throughout the phase, so it stays out of release builds.
  </action>
  <verify>
    <automated>cargo test -p bauded --lib manager:: && cargo test -p bauded --lib && cargo clippy --all-targets -- -D warnings</automated>
  </verify>
  <acceptance_criteria>
    - All ten call sites construct the helper; every `manager` test passes unchanged in behavior.
    - The helper holds the redirect guard as a field, so the redirect lives as long as the fixture.
    - Two helpers constructed in one test have different roots.
    - Any preamble copy that did more than the shared shape kept its extra setup at the call site, and that divergence is recorded in the plan summary.
  </acceptance_criteria>
  <done>A `bauded` fixture is one construction, and the redirect it establishes cannot outlive or under-live it.</done>
  <reversibility rating="reversible">A test-only refactor; the ten preambles are recoverable from history and no production code is touched.</reversibility>
</task>

<task type="auto">
  <name>Task 2: Assert a full suite run leaves the real config, `~/.claude`, and worktrees root untouched</name>
  <files>scripts/assert-real-roots-untouched.sh, .github/workflows/ci.yml</files>
  <read_first>
    - `.github/workflows/ci.yml:17-24` — the existing `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test -- --test-threads=1` steps, and the matrix of runners they execute on.
  </read_first>
  <precondition>CI runners provide a writable HOME; the script must operate on whatever real roots resolve on the runner rather than assuming the developer's paths exist.</precondition>
  <action>
Write `scripts/assert-real-roots-untouched.sh` as the suite-level statement of the phase goal.
It takes a mode argument: a "before" mode that records a fingerprint of the three real roots,
and an "after" mode that recomputes the fingerprint and exits non-zero if anything changed.

Fingerprint the real config dir, the real `~/.claude`, and the real managed worktrees root.
Resolve each one through the same XDG-then-home chain the Rust resolvers use, so the script
and the code agree about what "real" means on a given machine. Record, per root, a sorted
listing of entries with their sizes and modification times, and hash it. Treat a root that
does not exist as a distinct recorded state, not as an error — CI runners will not have
them — and treat "did not exist before and does not exist after" as a pass while "did not
exist before but exists after" is a failure. A test run that *creates* one of these
directories is exactly the leak this phase closes.

Make the failure output name which root changed and print the differing entries, not just a
hash mismatch. A bare hash comparison tells a developer that something leaked but not what,
and the diagnostic is the part that gets used.

Capture the exit status of the comparison directly and let it propagate. Do not pipe the
comparison into another command and read the status afterwards — that reports the status of
the last command in the pipeline and masks the real failure.

Wire it into `.github/workflows/ci.yml` as a step immediately before the existing full-suite
step and another immediately after it, with the "after" step configured to run even if the
suite itself failed. A suite that fails *and* leaks is the case most worth catching, and a
step that only runs on success would miss it.

Run the pair locally against a full `cargo test -- --test-threads=1` and record in the plan
summary whether any root changed. This is the measurement that decides whether the phase goal
is actually met; if a root does change, that is a finding for gap closure, not something to
work around by loosening the script.
  </action>
  <verify>
    <automated>bash scripts/assert-real-roots-untouched.sh before && cargo test -- --test-threads=1; status=$?; bash scripts/assert-real-roots-untouched.sh after; after=$?; test "$status" -eq 0 -a "$after" -eq 0</automated>
  </verify>
  <acceptance_criteria>
    - The script exits zero across a full suite run with no change to any of the three real roots.
    - Deliberately touching a file under one of the roots between the two invocations makes the script exit non-zero and name that root — the check is falsifiable.
    - A root that is absent before and after is a pass; a root created during the run is a failure.
    - CI runs the "after" step even when the suite step fails.
    - The full-suite result and the assertion result are reported independently, neither masking the other.
  </acceptance_criteria>
  <done>The phase goal is asserted at suite level by a check that fails when the suite touches a real root.</done>
  <reversibility rating="reversible">A new script and two CI steps; removing them restores the prior pipeline exactly.</reversibility>
