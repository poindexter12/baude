<objective>
Make workspace identity resolvable per fixture instead of once per process, so concurrent
fixtures cannot share or race one identity seeded from the developer's real environment.

Purpose: `ACTIVE: OnceLock<Workspace>` is the last process-wide cache in the isolation
path. Whichever fixture calls `active()` first pins the identity for the whole test binary,
and that identity is derived from the developer's real config. Because
`git::managed_default_worktree_path` composes `<base>/<workspace>/repository-<key>`, a
pinned identity also pins the directory every later fixture writes into.

Output: a thread-local override checked ahead of the retained `OnceLock`, and `initialize`
taking its config by parameter.
</objective>

<research_deviations>
**`active()` returns `&'static Workspace`, which a `thread_local!` cannot hand out.**
D-07 locks the signature, and a thread-local cannot produce a `&'static` reference to its
own contents. The resolution, compiled and verified in RESEARCH Finding 3, is to leak the
per-fixture `Workspace` with `Box::leak` and store the resulting `&'static` reference —
which is `Copy`, so a `Cell` suffices and no `RefCell` borrow can escape.

This is a genuine leak, and it is acceptable here for two reasons that must both hold:
it is bounded by fixture count rather than by call count, and it lives entirely inside
`cfg(any(test, feature = "test-support"))` code, so it never reaches a shipped binary.
`Workspace`'s fields are already `'static`-compatible (`String`, `&'static dyn Backend`,
`Option<String>`, `Option<u16>`), so nothing about the type needs to change.

**D-08 is implemented as a containment check, not an override-presence check.** CONTEXT.md
says a test reaching `active()` with no override "panics via the escape guard." Taken as
override-presence, that would abort the existing dogfood test, which isolates by `HOME` and
`XDG_DATA_HOME` rather than by thread-local and legitimately resolves identity from
environment. Plan 01's `assert_contained` is the containment form, and this plan uses it:
identity may fall through to the production path when the resolution demonstrably sits
inside `BAUDE_TEST_FIXTURE_ROOT`, and fails otherwise. The intent of D-08 — no silent
fallback to the developer's configured identity — is preserved exactly.
</research_deviations>

<decision_collision>
## D-06 and D-07 collide at `active()`, and this is the resolution

**The collision.** `baude-core/src/workspace.rs:206-222` reads, today:

```
pub fn initialize(hint: Option<&str>) -> &'static Workspace {
    ACTIVE.get_or_init(|| resolve_with_hint(…, &crate::persist::load_config(), …))
}

pub fn active() -> &'static Workspace { initialize(None) }
```

`active()` **is** the lazy initializer — it is one line delegating to `initialize`, and
`initialize` reads the config from disk inside the `OnceLock` closure. D-06 requires
`initialize` to take the config by parameter. D-07 requires `active()`'s signature to stay
`fn active() -> &'static Workspace`. Both cannot hold while `active()` remains a delegation:
once `initialize` demands a config argument, `active()` has none to pass.

The obvious improvisation — `active()` calling `persist::load_config()` itself — is
**forbidden**. It relocates the real-config read from `initialize` to `active()` without
removing it, so the identity path still reads config on every uninitialized resolution,
which is precisely what D-06 exists to stop and what hollows out Success Criterion 2.

**The resolution: split the two roles `active()` currently conflates.** `initialize` is the
*seeder*; `active()` becomes a pure *reader* that no longer calls it.

1. `initialize(config: &Config, hint: Option<&str>) -> &'static Workspace` — the only
   function that seeds `ACTIVE`, and it reads no config of its own (D-06).
2. `active() -> &'static Workspace` — signature and return type untouched (D-07). Its body
   becomes a three-step resolution, and it **stops being a delegation to `initialize`**: the
   first two steps return without reaching `initialize` at all.
   a. the thread-local `&'static Workspace` override, under the test-support cfg;
   b. `ACTIVE.get()`, the already-seeded production identity;
   c. neither present — the **uninitialized-bootstrap path**, described below, which is the
      only arm that still reaches `initialize`.
3. Every production entry point calls `initialize(&config, hint)` before any reader runs, so
   step 2c is unreachable in a correctly wired binary. Task 2 enumerates and wires them.

**The bootstrap path (step 2c), stated so the executor does not improvise it.** It is the
one place a config read survives, and it is a compatibility shim for an entry point that
failed to initialize — not part of identity resolution. It (i) calls
`testing::assert_contained` on the config path first, so under the test-support cfg a test
that reaches it with no override and no containment aborts (D-08); and (ii) then seeds
`ACTIVE` by calling `initialize(&crate::persist::load_config(), None)` — reproducing today's
behavior exactly for any production caller that slipped through. It is not a silent
fallback: it is guarded in test builds and dead in production once task 2 lands.

**Task ordering inside this plan.** Task 1 adds step 2a and restructures `active()` into the
three-step reader while `initialize` still has its current one-argument signature, so step 2c
reads `initialize(None)` at the end of task 1. Task 2 changes `initialize`'s signature and
updates step 2c to pass the loaded config, together with the production call sites. Neither
task leaves the crate uncompiling, and the interim state is stated here rather than
discovered.
</decision_collision>

builds a `Workspace`, hands it to `Box::leak` to obtain the `&'static` reference, stores

restores the previous value on drop. Store the reference, never the box — the reference is
`Copy`, which is what lets a `Cell` hold it and keeps any borrow from escaping the
thread-local.

Keep the resolution order strictly override-first. `active()` has roughly 27 call sites
across all three crates and the internal change is what keeps them untouched; do not thread
a parameter through any of them.

Write the concurrency test as two threads spawned inside one `#[test]`, each constructing
its own override *inside its own thread body*. Thread-locals do not cross a
`std::thread::spawn` boundary, so an override constructed on the parent thread would not be
visible in either child and the test would prove the opposite of what it claims. Gate the
two threads on a barrier so the overlap is real rather than incidental.

Do not write a test asserting that an override set by one `#[test]` is invisible to the
next. libtest already allocates a fresh thread per test, so that assertion passes on
today's unchanged code and certifies nothing. The property that actually fails today is the
concurrent one above: with a process-wide `OnceLock`, both threads resolve the same
identity.

Add a direct assertion that `git::managed_default_worktree_path` composes the same path for
a given identity and repository key as it does today. The identity feeds that composition,
so a change in resolution order that altered it would silently relocate every managed
worktree.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test fixture -> process-wide identity cache | A single `OnceLock` write by the first fixture determines the directory every later fixture in that binary writes into |
| developer real config -> test identity | Identity seeded from `load_config()` imports the developer's configured workspace name into the test's path composition |

| T-08-06 | Information Disclosure | identity seeded from the developer's real config | high | mitigate | `initialize` takes config by parameter so fixtures supply a literal and the identity path performs no config read (task 2) |
