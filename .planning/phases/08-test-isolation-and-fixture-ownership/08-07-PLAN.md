  <action>
Add a `worktrees` arm to the hand-rolled dispatch in `baude/src/main.rs`, alongside the
existing subcommand arms and before anything touches the terminal. Follow the established
shape exactly: match on `args.get(1)`, read any flags by scanning `args`, and exit through
`std::process::exit`. Do not introduce an argument-parsing dependency — this repo has none,
all four existing subcommands are dispatched by hand, and a whole parser tree for one
dev-facing verb is not a trade this phase should make.

The verb naming is `baude worktrees scan`, resolving D-19. Support a prune flag and a
separate explicit confirmation flag, so removal requires two distinct opt-ins on one command
line and neither alone does anything destructive (D-15). Support a JSON output flag as well;
the default output is a grouped human summary — counts per workspace and per verdict, with
the candidate paths and their evidence listed beneath — and JSON is the scriptable form of
the same data.

Update the `--help` subcommand list at the top of the file to include the new verb. The help
string and the dispatch are a matched pair; a verb that dispatches but is undiscoverable is
half-shipped.

This arm lives in `baude` only. `bauded` is headless and has no operator present to approve a
removal, so exposing a destructive verb there would be a path to unattended deletion. Do not
add a corresponding arm to `bauded`.

Add a test asserting that the scan path is read-only: run the subcommand's entry function
against a fixture tree with no prune and no confirmation flag, and compare the tree before
and after.

For manual acceptance, run `baude worktrees scan` against the developer's real tree, review
the grouped summary, and confirm that nothing was removed and that the two live `claude`
directories holding real checkouts are not reported as removable. Record the observed counts
in the plan summary.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI operator -> real data root deletion | The only interface in this codebase that can invoke a removal under the developer's real data root |
| command-line flags -> destructive action | A single mistyped or shell-expanded argument must not be able to authorize a deletion |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-17 | Elevation of Privilege | destructive verb reachable from the headless daemon | high | mitigate | The arm is added to `baude` only; `bauded` has no operator present to approve a removal and gets no corresponding verb (task 1) |
| T-08-18 | Tampering | single-flag accidental deletion | high | mitigate | Two distinct opt-in flags required on one command line; neither alone removes anything, and the default path is preview-only (task 1) |
| T-08-15 | Repudiation | removals with no account of what was refused and why | medium | mitigate | The grouped summary and the JSON output both carry plan 05's per-candidate outcome record, including refusals and their reasons (task 1) |
| T-08-19 | Information Disclosure | JSON output containing repository paths | low | accept | The output describes the developer's own local tree on their own machine and is printed to their own terminal; no transmission surface exists |
</threat_model>
