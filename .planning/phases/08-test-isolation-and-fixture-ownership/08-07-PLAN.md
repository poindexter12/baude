  <action>
Add a `worktrees` arm to the hand-rolled dispatch in `baude/src/main.rs`, alongside the
existing subcommand arms and before anything touches the terminal. Follow the established
shape exactly: match on `args.get(1)`, read any flags by scanning `args`, and exit through
`std::process::exit`. Do not introduce an argument-parsing dependency — this repo has none,
all four existing subcommands are dispatched by hand, and a whole parser tree for one
dev-facing verb is not a trade this phase should make.

The verb naming is `baude worktrees scan`, resolving D-13/D-19. Define these exact options:
`--json` for output, `--prune` to request re-verification, `--report <path>` to supply the
previous preview, and `--yes` as the separate confirmation (D-15). The default prints a
grouped human summary with counts per workspace/verdict and paths/evidence beneath it.
`--json` emits the complete core ScanReport to stdout, with diagnostics only on stderr, so
the operator can save and inspect it before a later command. Do not write hidden approval
state or mutate the scanned roots while producing a preview.

Document the two-invocation flow in help: first `baude worktrees scan --json` with its output
saved by the operator to a report file, inspect that file, then
`baude worktrees scan --prune --report <path> --yes`. These are CLI documentation examples,
not instructions to delete the historical dataset during phase execution. `--prune`
requires `--report`; missing input, unsupported format, duplicate/unknown options, a
missing option value or a foreign-root report exits nonzero without removal. `--yes`
without `--prune` is a usage error. `--prune --report <path>` without `--yes` performs
re-verification and reports outcomes but removes nothing. Reject --report without --prune
so report consumption cannot be confused with a new scan.

Deserialize the saved report and pass it unchanged to core `prune_at` with independently
resolved roots and the confirmation bool. Do not call fresh scan to create the candidate
list for prune. Print core per-candidate outcomes, including changed-proof and newly
blocked refusals. The saved report is comparison input, never trusted deletion authority;
core must re-derive ownership as plan 05 specifies.

4. Candidates still holding a gitdir go through the verified-removal path, not direct
   directory removal.

| Boundary | Description |
|----------|-------------|
| CLI operator -> real data root deletion | The only interface in this codebase that can invoke a removal under the developer's real data root |
| command-line flags -> destructive action | A single mistyped or shell-expanded argument must not be able to authorize a deletion |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-17 | Elevation of Privilege | destructive verb reachable from the headless daemon | high | mitigate | The arm is added to `baude` only; `bauded` has no operator present to approve a removal and gets no corresponding verb (task 1) |
| T-08-18 | Tampering | single-flag accidental deletion | high | mitigate | Two distinct opt-in flags required on one command line; neither alone removes anything, and the default path is preview-only (task 1) |
| T-08-15 | Repudiation | removals with no account of what was refused and why | medium | mitigate | The grouped summary and the JSON output both carry plan 05's per-candidate outcome record, including refusals and their reasons (task 1) |
| T-08-25 | Tampering | serialized preview supplied by the CLI | high | mitigate | Require --report for prune, deserialize the complete core contract, pass independent roots and prior candidate proofs to core re-verification; no fresh scan substitution or trust in serialized verdicts (task 1) |
