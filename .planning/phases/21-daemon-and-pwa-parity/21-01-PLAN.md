<objective>
Tracer: one checkout row removed end to end over REST, production quality, no stubs. `Manager::preview_removal` and `Manager::remove_rows` wrap `baude_core::removal::{preview_removal, remove}` with the runtime custody, recheck-under-lock and rollback posture Phase 20 proved in the TUI, and `api.rs` exposes them as `POST /removals/preview` and `POST /removals` under the daemon's plain-text error convention. The slice touches every layer this phase modifies in the daemon — `Manager` state, the axum router, the state file on disk, the live process group — and proves the shape before the expansion plans add row kinds (21-09, 21-10), the drift matrix (21-03), SSE (21-04), the hierarchy projection (21-02) and the two clients (21-05, 21-07, 21-08).

This plan implements D-01, D-02, D-03 and D-04 for the checkout kind. Execute body: the body of `POST /removals` is the preview `RemovalReport` JSON echoed verbatim, so the PWA and the TUI remote client resend exactly what they rendered; the daemon reads `target` and compares `rows_removed`, `runtimes_killed` and `paths_deleted`, and ignores the rest (resolves RESEARCH assumption A3 without a second wire type).

**What makes this replan cycle different.** The previous 21-01 went byte-identical through two review cycles. Two HIGH findings are properties of this tracer's own seams and are discharged here, in task text, not deferred:

- **HIGH #1 — survivor metadata.** Every ordinary daemon save is `StateFile::new(self.state_for_save())` (`bauded/src/manager.rs:719`), and `state_for_save` (`:779`) merges live runtime metadata from `runtime_checkouts` + `self.sessions` back into each persisted checkout. `baude_core::removal` builds its own candidate and hands the closure a `StateFile` over it (`baude-core/src/removal.rs:445`, `removal.rs:1035-1038`), so a closure that writes core's candidate straight to disk skips that merge and can persist a stale `archived`, `name`, `branch` or `resume_id` for a session that was never part of the removal. The closure here merges survivor metadata into a clone of core's candidate before writing. Task 2 proves it: archive session B, remove A, reload from disk, B is still archived.
- **HIGH #2 — fixture liveness.** The daemon resolves permission flags before spawning and the default resolver appends `--dangerously-skip-permissions` (`baude-core/src/permission.rs:88-98`, applied at `bauded/src/manager.rs:1231`). A bare `sleep 30` rejects that argument and exits, so a non-zero persisted pid and a listed session prove nothing. The fixture command is the shell wrapper the repo's own Docker smoke already uses for exactly this reason (`.github/workflows/ci.yml:78-85`: `sh -c "sleep 60"`), and the test probes the pid with `ps` before and after the execute call instead of inferring liveness.

Purpose: the single source of truth for removal stays `baude-core`; the daemon owns handles, the lock, the persist adapter and status mapping only.
Output: compiled `Manager` and `api` code with HTTP tests that drive a genuinely live runtime through preview and execute against an isolated fixture repository and state file.
</objective>

<flagged_assumptions>
1. **Preview holds no repository reservation, deliberately.** Core's doc says callers hold `RepositoryReservations` from before `select_rows` until the function returns (`baude-core/src/removal.rs:461-464`). `Manager::preview_removal` is a bare `&self` delegate, which reads as non-compliant until you work it out: the handler holds the global `Arc<Mutex<Manager>>` guard for the whole call (`bauded/src/manager.rs:38`, `lock()` at `:106`), so the preview is already atomic against every other daemon mutation, and `remove_rows` reserves before its own recheck and before core's `select_rows`. Recorded here so an executor does not "fix" it by adding a reservation that then self-deadlocks against `remove_rows`.
2. **`RuntimeHandleMissing` is reachable on the daemon and is NOT covered here.** `restore_loaded` (`bauded/src/manager.rs:526-570`) can leave a checkout in `repository_state` with no `runtime_checkouts` entry while its persisted `owned_runtime` is still set, which makes core's `preflight` return `RuntimeHandleMissing`. Per the outline, 21-03 owns driving it and choosing its status deliberately. This plan maps it to 500 plain text so it is never an unmapped fall-through, and says so rather than implying coverage.
</flagged_assumptions>
