<objective>
**Make a daemon folder session a real standalone row, and wire daemon admission to the suppression store.**

1. **The headline.** A plain folder that is not a git repository, opened over `POST /sessions`, is
   stored as one standalone row with a live owned runtime, is served by `GET /rows` with a
   `session_id`, survives a daemon restart, and is removed end to end over the two existing routes:
   one row dropped, one runtime killed, the folder kept. This is the HIGH no earlier plan owned
   (outline HIGH #4): today that folder goes through `record_checkout_intent`, which manufactures a
   repository and a checkout when git discovery fails, the daemon has only a checkout runtime
   registry, and restore iterates checkouts.
2. **The pin.** D-11: daemon admission goes through the shared `baude_core::suppression` helper. An
   explicit admission lifts the entry for exactly the path it admits; nothing else lifts or admits.
   The path form is read back out of the executed report's `ClearedItem`, and the parent-removal half
   is asserted in the direction a user sees: the child's entry is gone.

Purpose: API-01 names four row kinds and three were reachable. Without this plan a test could only
seed a synthetic inactive standalone row, which proves removal of state no real daemon ever stores.
API-03 depends on it too: the PWA offers remove on a standalone row only if `/rows` serves one with a
durable key and a `session_id` to join on (D-09 Option B, D-10).

Output: `runtime_standalones` beside `runtime_checkouts`, a routed plain admission, standalone
custody on every path that starts or ends a runtime, restore over standalone rows, the suppression
lift on explicit admission, and the `standalone_*` and `suppression_*` tests in `bauded/src/api.rs`.

**What makes this replan cycle different.** The cycle-2 plan seeded an inactive standalone row with a
test-only helper and removed it. The codex lane called that out as proof over synthetic state, and it
was right. Every fixture here is created the way a user creates it: a real directory holding a real
file, opened through `POST /sessions`, with a live agent process.

**D-09 is settled as Option B.** `checkout_key` and `standalone_key` are served only by `GET /rows`;
clients join on `session_id`. `GET /sessions` gains no field in this plan and the compatibility test
at `bauded/src/api.rs:1002-1010` is not edited. Tests resolve a standalone key the way a client does:
from the `/rows` entry whose `session_id` equals the id `POST /sessions` returned.
</objective>

## Standalone rows on the daemon — admission, custody and the suppression store

No route, handler, request body or response field is added. What changes is which row a plain
`POST /sessions` stores, who owns the runtime it starts, and what the suppression store sees.

### Plain admission (the `worktree: null` arm of `Manager::create`, persisting manager only)

The request path is expanded and canonicalized first, as it is today. The canonical path then takes
the first route that matches, in this order. This is the TUI's order (`baude/src/app.rs:6054-6106`)
with one daemon-only route, the third, for state earlier daemons wrote. `route_plain_admission` in
Task 1 is this table and nothing else.

| # | Condition on the canonical path | Route | Row stored |
|---|---|---|---|
| 1 | A standalone row already has this `canonical_path` | reuse that row | none added; a live session is returned as it is, a closed row is reopened |
| 2 | `git::discover_repository` returns a snapshot | the checkout arm, unchanged, with 21-09's role rule | a checkout |
| 3 | `git::discover_repository` returns `RepositoryDiscoveryError::NotRepository`, and a checkout row's `observed_path` or a repository row's `observed_main_worktree` already equals the path | the checkout arm, joined to the repository row that already holds the path | a checkout in that repository; no repository row is added |
| 4 | `git::discover_repository` returns `RepositoryDiscoveryError::NotRepository`, and no stored row holds the path | standalone admission | one standalone row |
| 5 | `git::discover_repository` returns any other error | refused; nothing stored, nothing spawned | none |

**Why route 3 exists.** Core rejects a state in which a standalone path equals a checkout's path or a
repository's main worktree (`StandaloneCheckoutPathConflict`, `baude-core/src/repository.rs:1040-1052`),
and a rejected state fails every later save. A daemon before this plan stored a folder as an
unavailable repository plus a checkout. Such a folder stays on that shape until its repository row is
removed; only then is the path free for route 4. Route 3 never creates a repository row: it can only
match one that is already stored.

**Why route 5 refuses.** `NotRepository` is the one outcome in which git itself says there is no
repository (`baude-core/src/git.rs:340-346`). Any other error means the daemon does not know what the
folder is, and a guess in either direction stores a row of the wrong kind. The request is answered by
the existing error mapping of `create_session`; this plan pins "not 201 and nothing stored", not a
status.

**The non-persisting manager is untouched.** `Manager::new(cmd, false)` stores no rows at all and
keeps spawning through `spawn` (`bauded/src/manager.rs:905`).

### Custody (who owns a folder session's runtime, at every use site of the registry)

`runtime_standalones: HashMap<StandaloneKey, u64>` sits beside `runtime_checkouts`
(`bauded/src/manager.rs:128`). A session id is in at most one of the two. Each place the checkout
registry is read or written gets a decided standalone behaviour:

| Use site | Standalone behaviour |
|---|---|
| launch registration | the row records `Launching(generation)` with the owned runtime before the launch is released, then `Running(generation)` with `ever_launched` set; both are durable saves with rollback. A failed launch returns the row to `Active` with no owned runtime |
| `state_for_save` | name, shell-open, archived, archived-by-user and resume id are copied from the live session onto the row, as checkouts do |
| `ensure_runtime_capacity` | a standalone key and a first-seen order are allocated on a clone of the state; exhaustion refuses before anything is spawned |
| `Manager::rows` | the standalone entry's `session_id` is the registry's id, `null` when the row has no live session |
| `Manager::remove_rows` | the live session of every `RowKey::Standalone` in the fresh report is handed to core as a `RowRuntime`; restored in id order when core returns an error; the registry entry is dropped when core returns the report |
| `Manager::remove` (`DELETE /sessions/{id}`) | the runtime is torn down and the row is **kept**, closed: lifecycle `Inactive`, no owned runtime, session metadata snapshotted first |
| `Manager::restart` | an exited folder session goes through `reopen_standalone`, which clears the exited runtime's ownership and launches again under the resume rule |
| `reconcile_early_targeted_resume_exits` | a targeted resume that dies at once has its retained resume id cleared on the standalone row and is closed through `close_standalone`; the row is kept, closed |
| restore | rows that were `Active`, `Launching` or `Running` are relaunched after any recorded runtime is torn down by recorded identity; `Stopping` and `ProtectedTeardown` rows are torn down and not relaunched; `Inactive`, `Missing` and `Io` rows are left alone |

**Resume rule.** A row that was never launched starts fresh. A row that was launched before starts in
the mode `lifecycle::resume_mode` returns for its retained resume id. This is the TUI's rule
(`baude/src/app.rs:2241-2248`), not a new one.

**One row per folder.** Core allows one standalone row per canonical path
(`DuplicateStandalonePath`, `baude-core/src/repository.rs:1036`). Route 1 is how the daemon honours
that.

### The suppression store (D-11)

- **Write rule: inherited, untouched.** Core writes an entry only for a checkout removed while its
  repository row remains, keyed on that checkout's stored `observed_path`, and drops a repository's
  child entries when the repository row is removed (`baude-core/src/removal.rs:559-609`, `:755-806`).
  A repository parent and a standalone row write no entry of their own. This plan adds no write.
- **Lift rule: added here.** Every explicit admission through `Manager::create` calls
  `suppression::lift` over `persist::config_dir()` with the path the admitted row stores:
  `canonical_path` for a standalone row, `observed_path` for a checkout row from either arm. That is
  the same field core passed when it wrote the entry. `<flagged_assumptions>` item 14 records the one
  case in which the two keys can still differ.
- **A lift is advisory.** Its error never fails an admission, which is the TUI's stance
  (`baude/src/app.rs:2374-2379`).
- **Nothing else lifts.** Restore, reopen, the restart route and legacy migration do not call `lift`.
- **No sweep, so no sweep guard.** The daemon has no discovery sweep that admits rows it was not asked
  for; its only row-creating paths are `create` and the one-time legacy migration. The TUI's
  `is_suppressed` guard has no daemon call site to protect. This is asserted by behaviour: a restart
  after a removal serves no row for the removed path and leaves its entry in the store.

**How the tests know the expected value.** A suppressed path is never rebuilt by the test. It is the
`path` of the `ClearedItem` whose `kind` is `ClearingKind::SuppressionAdded` in the executed report,
read by deserializing the 200 body into `baude_core::removal::RemovalReport`. The store is read with
`suppression::is_suppressed(&persist::config_dir(), path)`, which the test harness redirects under
the test root (`bauded/src/api.rs:721-742`).

1. **Rows earlier daemons stored for a folder are not converted.** A `daemon-state` file written before this plan holds a folder session as an unavailable repository plus a `managed_branch` checkout. This plan stops creating that shape and leaves stored instances alone: they are served verbatim, they keep working through route 3, and Task 3 proves they are removable with the folder kept. Converting them at restore is a state migration the outline row does not name. It is surfaced to the orchestrator as an open decision, the same stance 21-09 took for mis-roled main rows. Not converting is fully reversible.
2. **Legacy flat-file migration still yields an unavailable repository for a folder.** `reconcile_legacy_session` (`bauded/src/manager.rs:155-178`) answers through core's `LegacyReconciliation` (`baude-core/src/persist.rs:305-318`), which has an available and an unavailable outcome and no standalone one. Changing that is a core contract change outside this plan's files. The migrated shape is the one item 1 describes and is handled the same way.
3. **One session per folder is a behaviour change.** Before this plan two `POST /sessions` on one folder stored two checkout rows and ran two agents. Core permits one standalone row per canonical path, so the second request now returns the live session with the handler's unchanged success status. Refusing the second request instead is the alternative; it is surfaced to the orchestrator, and is reversible either way because nothing persisted depends on the choice.
4. **A closed folder row reopened by `POST /sessions` resumes.** That is the TUI's rule. A daemon before this plan always started a fresh agent for a plain create.
5. **Discovery errors other than not-a-repository now refuse.** Before this plan every discovery error fell through `.ok()` into a fabricated repository. No realistic fixture produces such an error on demand, so that route is proven on the pure router with a real error value, not through HTTP.
6. **A folder holding a dangling `.git` file is a standalone row.** git answers "not a git repository" for a worktree directory whose repository was deleted, which discovery reports as `NotRepository` (`baude-core/src/git.rs:340-346`). Task 3 creates that folder and asserts the row kind, because it is the shape a user really leaves behind.
7. **The TUI and the daemon share one suppression store and keep separate state files.** A path the TUI removed can still be a row in `daemon-state`, and the daemon relaunches it at restart because it was never removed from the daemon's own state. This plan does not change that; it is surfaced, not decided. The two clients also name the lifted path differently: the TUI lifts the worktree root of the path it admits (`baude/src/app.rs:2374-2379`), and the daemon lifts the stored path of the row it admits, which is the field core passes when it writes an entry for a daemon row. They agree when the admitted path is a worktree root and can differ for a subdirectory of one.
8. **`restore`'s returned count includes relaunched standalone rows.** Existing tests that assert the count use checkout-only fixtures and are unaffected.
9. **Status codes on the losing side are 21-03's.** Where a test needs a request to be refused, it asserts "not 200" (or "not 201") and an unchanged world. The 409 / 500 / 503 matrix and the status for a missing runtime handle are 21-03's and are not pinned here.

Task 1 names the candidates and the two permitted treatments. This is the one place this plan edits tests it did not write, and it is bounded to tests whose fixture is a non-repository folder on a persisting manager.

13. **The `Stopping` / `ProtectedTeardown` arm of restore has no daemon-level test.** A row is in either state only between two saves inside one close. No fixture a user could produce leaves a state file there on demand, and writing one by hand would be the synthetic state this replan cycle exists to stop. The arm mirrors the TUI's `restore_standalones` (`baude/src/app.rs:2263-2360`), which carries the tested precedent. Stated so the gap is a known one and not a silent one.
14. **A suppression entry's key depends on whether the directory existed when it was written.** `folder_key` (`baude-core/src/breadcrumbs.rs:116-121`) canonicalizes the path at the moment it is called and falls back to the spelling it was given when the directory is missing. ## Spec-less edge lift (§A/§C), the API-01 row for the standalone kind

Phase 21 has no SPEC, so `EDGE_ABSENT=1`. The classified API-01 row ("two concurrent REST removals of
the same row, or a removal interrupted mid-flight") was authored for the checkout kind in 21-01 and
for the fan-out kinds in 21-09. It is lifted here for the standalone kind, verification explicit:

- **Concurrency.** Two `POST /removals` echoing one previewed standalone report commit exactly once.
  Asserted by `standalone_concurrent_removals_of_one_folder_commit_once`.
- **Interrupted mid-flight, runtime half.** A standalone removal has no disk stage, so the only state
  an interruption can leave behind is persisted ownership of a runtime. The daemon is restarted while
  the row still records a live owned runtime; restore tears that runtime down by recorded identity,
  relaunches, and the removal then succeeds. Asserted by
  `standalone_restart_tears_down_the_recorded_runtime_and_relaunches`.
- **Interrupted mid-flight, world-changed half.** The folder is deleted by hand while the daemon is
  down. The row is still served and the removal converges. Asserted by
  `standalone_row_whose_folder_vanished_is_still_removable`.
