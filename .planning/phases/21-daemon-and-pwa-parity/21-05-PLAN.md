<objective>
Wire the PWA to the removal contract: a hierarchical row list from `GET /rows`, a remove control on
every row that has a durable key, a preview-then-confirm modal over `POST /removals/preview` and
`POST /removals`, and a `GET /events` subscription that drops rows in every open tab.

This plan is controller and wiring only. It calls the 15 exports of `BaudeRemoval` from 21-07 and
re-implements none of them. It owns three review HIGHs: #5 (a pending refresh resurrects removed
rows), #6 PWA share (409 child names from a refetched `/rows`), #7 (verifies judged through a pipe).

Purpose: API-03 for the phone client, plus the PWA half of API-02.
Output: `bauded/web/removal-controller.js` with a `node --test` suite, `app.js` wiring, the wide
modal CSS, and asset registration in `index.html`, `sw.js` and `bauded/src/web.rs`.

**Design decision made here, recorded as an assumption (reversible).** The controller lives in its
own dependency-injected file rather than inline in `app.js`. `app.js` touches `document` at line 5
and cannot be loaded by Node, so inline controller logic could only be human-verified. Injecting
`request`, `openEvents`, `now`, `onChange`, `notify` and `onSessionGone` lets `node --test` drive the
real state machine, which turns HIGH #5 and HIGH #6 from manual checks into automated ones. Cost:
one more served asset.

**Settled inputs.** D-09 = Option B: `checkout_key` comes only from `/rows`; the PWA joins `/rows`
entries to `/sessions` entries on `session_id` = session `id`; `/sessions` is unchanged. `/events`
(21-04): named event `rows_removed`, one `data:` line holding a `RemovalReport`, exactly one frame
per committed removal including the SavedDegraded 200, none on preview/409/500/503, no `id:`, no
replay, silent skip-on-lag, keep-alive comment frames, no ordering against the POST response.
Statuses, from the table in `21-03-PLAN.md` (rows at :94 and :100-103, re-grep): 200 report; 404
plain text when the target row does not exist, which includes an already-executed report and the
loser of two identical removals; 409 a fresh report and the only JSON error body; 500 plain text,
runtime survived; 503 plain text for a failed save, a missing runtime handle, blocked persistence
and a busy repository (text beginning `repository busy:`). A blocked daemon answers 503 before 404.
500 and 503 are retryable; 404 is not an error to retry, it means the row is already gone. After a
503 from a failed save the retry answers 409 with the path under `already_removed`. No error body
other than a 409 is ever parsed as JSON.
</objective>

<error_text_rule>
The PWA share of the register 21-06 records in its `<error_text_register>` block. Rule 2 there: a
row key in Rust debug form never reaches the user, in any client.

- **Tokens.** `Repository(RepositoryKey(n))`, `Checkout(CheckoutKey(n))`, `Standalone(StandaloneKey(n))`,
  with `n` one or more ASCII digits and the inner word matching the outer one.
- **Label.** The row's entry in `BaudeRemoval.rowsIndex` of the controller's rows, found through
  `BaudeRemoval.rowKeyId`: `display_name`, followed by a space and the branch in parentheses when
  `branch` is a non-empty string. `zeta (feat/zeta)`; a row with no branch reads `zeta`.
- **Fallback.** The words `unknown row` when the index has no entry for the key, the entry has no
  usable `display_name`, or the number is not a safe integer. This is 21-06's wording, not 21-07's
  `<kind> <key>` label: that one stays where 21-07 put it, in the confirmation's rows-dropped list,
  where each unresolved row has to stay distinguishable. Do not unify the two.
- **The word before the token.** Where a token directly follows the whole word `row` and one space,
  that word and space are replaced with it, as 21-06 Task 3 does in the TUI, so one daemon text
  reads the same in all three clients: `row Checkout(CheckoutKey(7)): runtime survived the kill
  stage: still running` becomes `zeta (feat/zeta): runtime survived the kill stage: still running`,
  or `unknown row: runtime survived the kill stage: still running`.
- **Nothing else changes.** No rewording, no classification, paths exactly as sent, `tildePath` not
  applied (register rules 1 and 3). A text with no token comes back identical.
- **Where it applies.** Every value stored in `errorText` and every string handed to `notify`.
</error_text_rule>
