<objective>
Drift and failure matrix for the removal routes. 21-01 built `removal_error` and mapped every
`RemoveRowsError` arm; 21-09 and 21-10 proved the four row kinds and left every refused request as
"not 200". This plan drives each failure class through its real cause over HTTP, pins one status per
class, and proves the two properties the reviewers found unproven: that a body which **passes** the
D-04 recheck still cannot steer the daemon, and that a removal interrupted between its disk stage and
its save converges on retry.

One production change is planned: `RemovalError::RuntimeHandleMissing` moves from 500 to 503, chosen
deliberately (`<wire_contract>`). Everything else is test code and two `#[cfg(test)]` seams. If a test
exposes a defect in `Manager::remove_rows` or its recheck, the fix is in scope and lands where the
defect lives.

Purpose: API-01 says a client can remove any row over REST. That is only true if every way the
removal can fail leaves the daemon in a state the client can read and retry from, with a status the
three clients (21-05, 21-06, 21-08) can branch on.
Output: fourteen `matrix_*` HTTP tests in `bauded/src/api.rs`, the status table below, and the
recorded decision that resending a 409 body is deliberate idempotency.

**D-09 is decided: Option B.** `checkout_key` is served only from `GET /rows`; clients join on
`session_id`. Every key a test here needs is read from `GET /rows` joined on the `id` a
`POST /sessions` response returned, or from 21-01's `checkout_key_for_runtime_for_test`. No task
touches `SessionInfo` or the `/sessions` compatibility test.

<wire_contract>
## The status matrix for `POST /removals` and `POST /removals/preview`

This table is the contract 21-04, 21-05, 21-06 and 21-08 build against. No route, request field or
response field is added.

| Failure class | Source arm | Status | Body |
|---|---|---|---|
| Target row does not exist, including a report that was already executed and a target another client removed | `RemovalError::UnknownTarget` | **404** | plain text, the error's `Display` |
| A compared set differs from the fresh preview: `rows_removed`, `runtimes_killed` or `paths_deleted` | `RemoveRowsError::Drift` | **409** | JSON, the fresh `RemovalReport` with `planned: true` — the only JSON error body (D-03) |
| A runtime survived the kill stage | `RemovalError::RuntimeSurvived` | **500** | plain text |
| A directory could not be removed | `RemovalError::DiskRemoval` | **500** | plain text |
| A held handle is not the process the row records | `RemovalError::RuntimeIdentityMismatch` | **500** | plain text |
| The candidate state failed validation | `RemovalError::Validation` | **500** | plain text |
| The row records an owned runtime the daemon holds no handle for | `RemovalError::RuntimeHandleMissing` | **503** | plain text |
| The save failed before the replacement committed | `RemovalError::Persist` | **503** | plain text |
| Persistence is blocked after a state load failure | `RemoveRowsError::Blocked` | **503** | plain text |
| The repository is reserved by another mutation | `RemoveRowsError::Busy` | **503** | plain text beginning `repository busy:` |
| The save failed after the replacement committed | `PersistenceOutcome::SavedDegraded` | **200** | JSON report, `persistence` is `{"outcome":"saved_degraded","detail":…}` |
| Body is not a `RemovalReport` / `RemovalTarget` | axum `Json` rejection | axum's own 4xx | axum's own; no custom mapper |
| `POST /sessions` admission refused | `MutationError::Domain` through `create_session` | **400** | plain text (`bauded/src/api.rs:179`) |

**Reading the table as a client.** 404: the row is gone, drop it. 409: re-render from the body and
ask again. 500: a stage acted on a process or the disk and failed, or an invariant broke. 503: the
daemon could not carry the removal through because of its own state. D-15 gives 500 and 503 the same
client treatment (modal stays open, daemon text, Retry), so the split is for meaning, not branching.

**Why `RuntimeHandleMissing` is 503 and not 500 or 409.**
- Not 409: D-03 makes 409 the one JSON body, and 21-05 and 21-08 parse it as a report. The fresh
  report would equal the echoed one, so a client would re-render the same modal forever.
- Not 500: it is raised by core's preflight (`baude-core/src/removal.rs:863`) before any stage runs.
  Nothing was signalled, deleted or saved, which is unlike every other 500 in the table.
- 503 matches the daemon's existing precedent for "refused because of daemon state, nothing touched,
  cleared by an operator or a restart rather than by the client": `Blocked` is already 503 and is
  also not cleared by simply retrying.
- `RuntimeIdentityMismatch` and `Validation` stay 500: a held handle that is the wrong process, or a
  candidate core's own validator rejects, is an invariant break rather than a known operating state.

**What the daemon compares, and what it ignores.** Compared: `target` (to select), `rows_removed`,
`runtimes_killed`, `paths_deleted` (D-04). Ignored on input: `planned`, `paths_kept`,
`already_removed`, `cleared`, `clearing_failures`, `readers_parked`, `persistence` and any unknown
field. Every path, handle and row the daemon acts on comes from its own `repository_state` and
registries.
</wire_contract>

<flagged_assumptions>
1. **The outline's 200 case is worded in a way that cannot occur, and this plan implements the
   property behind it.** The outline row asks for "the 200 case where a bogus `paths_deleted` entry is
   echoed with otherwise-matching sets". `paths_deleted` is one of the three compared sets, so a bogus
   entry there is always drift and always 409. The claude-lane finding the row summarizes says what
   was meant: the three sets match exactly and the **uncompared** fields carry the bogus path. That
   is `matrix_drift_uncompared_fields_cannot_steer_the_daemon`. The 409 case is kept beside it.
2. **`RuntimeHandleMissing` is driven by a seam, and nothing here heals it.** Planning verified that
   `restore_loaded` only logs a failed reopen (`bauded/src/manager.rs:567`) and did not establish
   whether that leaves `owned_runtime` set, so a restart-shaped reproduction could not be written
   with a determinate assertion. `forget_runtime_handle_for_test` reproduces the stale runtime row
   directly. A row in this state stays unremovable over REST until the daemon's own state changes.
   Whether `remove_rows` should end a recorded runtime it holds no handle for is a behavior the
   outline row does not name; it is surfaced to the orchestrator as an open decision.
3. **Resending a captured 409 body stays executable, deliberately** (outline flagged assumption 3,
   the API-03 idempotency edge). A 409 body is a preview report; it executes whenever its three sets
   still equal the daemon's fresh preview, with no nonce and no expiry. That is the contract D-14
   depends on (the client re-renders and confirms the body it was handed). On a tailnet with auth
   deferred in `21-CONTEXT.md` this is accepted, recorded as T-21-40, and asserted rather than left
   implicit. The bound is state, not time: once executed, the same body is 404.
4. **Kill order inside a repository removal is assumed to follow the preview's `runtimes_killed`
   order.** `matrix_failure_parent_abort_keeps_every_handle_held` arms the failure on the row listed
   last. Its assertions hold in either order; only "one child stopped first" depends on it, and the
   test records which pid was dead rather than requiring it.
5. **Three arms are mapped and not driven at the daemon boundary:** `DiskRemoval`,
   `RuntimeIdentityMismatch`, `Validation`. Planning found no daemon-reachable real cause for the last
   two, and a hand-built error would break the rule that each status is driven by its cause. Core
   proves `DiskRemoval` at its own boundary (`baude-core/src/removal.rs:2089`, `:2161`). All three
   keep 21-01's 500 and appear in the table so no arm is unmapped.
6. **The teardown seam exists only in debug builds.** `Pty::fail_next_teardown_for_test` is behind
   `#[cfg(debug_assertions)]` (`baude-core/src/pty.rs:912-914`). Every verify here uses the default
   test profile; a `--release` test run would not compile these tests.
7. **`.planning/REQUIREMENTS.md:82` versus D-12** does not affect this plan; 21-06 corrects the line.

  save (`baude-core/src/removal.rs:454-456`), so an interruption between them leaves the row stored
  and the worktree gone. 21-09 proved convergence when a user removed the worktree by hand. This plan
  proves it when the **removal itself** was the interruption:
  `matrix_failure_persist_is_503_and_the_retry_converges`. Authored as a plain truth (verification:

- **API-03 idempotency, "the remove posted twice for the same row".** 21-02 authored the requirement
  row. The daemon half is recorded and asserted here: the second post of an executed report is 404
  and changes nothing; the resend of a 409 body executes. Plain truth (verification: explicit).
