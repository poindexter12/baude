<wire_contract>
## `GET /events` — the pinned contract 21-05 and 21-08 consume

| Item | Pinned value |
|---|---|
| Route | `GET /events`. No path or query parameter, no request body. 200, `content-type: text/event-stream`. Same no-auth tailnet posture as every other route |
| Scope | Daemon-wide. One stream per connection, not per session. Opened once by a client and never tied to a selected session |
| Event name | `rows_removed`, the SSE `event:` field. It is a named event, so a browser client must use `addEventListener("rows_removed", …)`; `onmessage` never fires for it |
| Data | One `data:` line holding the `RemovalReport` JSON, produced by the same serde derive as the `POST /removals` 200 body (D-06). Top-level field names: `target`, `planned`, `rows_removed`, `runtimes_killed`, `paths_deleted`, `paths_kept`, `already_removed`, `readers_parked`, `persistence`, `cleared`, `clearing_failures`. `planned` is `false`. `persistence` is internally tagged: `{"outcome":"saved"}` or `{"outcome":"saved_degraded","detail":"…"}` |
| Row identity | `rows_removed` is a list of `RowKey`, snake_case externally tagged: `repository`, `checkout`, `standalone`. A repository removal lists its children and the parent in one message. Per D-09 Option B the message carries **no names and no `checkout_key` on any session**: a client resolves a key to a name, branch or session id through `GET /rows` |
| Cardinality | Exactly one message per committed removal, including a `saved_degraded` commit. Zero for a preview, a 409, a 500 or a 503 |
| `id:` / `retry:` | Neither is sent. `Last-Event-ID` is ignored |
| History | None. A subscriber sees only removals that commit after its subscription exists. A reconnect gap is reconciled by polling `GET /rows` (D-08) |
| Keep-alive | `KeepAlive::default()`: an SSE comment frame, a line starting with `:`, on axum's default interval of 15 s. Clients ignore comment lines. A client read timeout must exceed that interval (21-08) |
| Lag | Channel capacity 64. A subscriber more than 64 events behind silently loses the oldest ones; the stream stays open and continues with the oldest retained event. No lag notice frame is sent |
| End of stream | Only when the daemon drops the sender, which is process shutdown |

The executor pastes one real frame, bytes as read off the response body, into the SUMMARY so both
client plans copy real values. If the pinned axum version's default keep-alive interval is not 15 s,
record the real value in the SUMMARY: 21-08's read timeout is derived from it.
</wire_contract>

## Flagged assumptions — not resolved by this plan

1. **API-02 edge, `unclassified` by the deterministic probe, status `unresolved`.** The probe text is
   "unclassified — review manually". It is not auto-resolved, no backstop marker is authored for it,
   and it is not dropped. What this plan assumes while it stays open, each a reading a human may
   overturn:
   - "Removal over REST" means `POST /removals` only. `DELETE /sessions/{id}` and the worktree
     removal route publish nothing, since D-06 defines the event as a `RemovalReport` and those routes
     produce none.
   - "Drops the rows without a refresh" is satisfied by a connected subscriber. A subscriber that
     missed a message through a reconnect, a late subscribe or lag converges only through its
     existing poll, per D-08. No replay, no `id:`, no lag notice.
   - No ordering is promised between the `rows_removed` message and the `POST /removals` response
     reaching the same client. The initiating client may see its own event first (21-05 handles it).
   A human classifying this edge should say which of the three, if any, API-02 actually requires.
2. **Keep-alive is pinned but not witnessed by an automated test.** Observing a 15 s comment frame
   needs tokio's paused clock, a dev-feature this plan does not add. The route is built with
   `KeepAlive::default()`; the interval is read from the pinned axum source and recorded.
3. **Lag is driven by synthetic events.** 65 real removals with live runtimes are not a fixture any
   user produces either; the flood goes through the real sender via `publish_for_test`, and the event
   that proves survival is a real removal over REST, read off the real response body.
</flagged_assumptions>
