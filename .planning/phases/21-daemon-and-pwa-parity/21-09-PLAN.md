## `role` and `branch` on `GET /rows` — the pinned values

21-02 fixed the field names and served both values verbatim, deferring their correctness here in so
many words. This section is that correction. **No field is added, renamed or removed**: the ten
checkout field names in 21-02's `<wire_contract>` stand.

| Field | Value after this plan | Source |
|---|---|---|
| `role` | `"main"`, `"primary_default"` or `"managed_branch"`: the stored `CheckoutRole` in its serde form (`baude-core/src/repository.rs:284`), served verbatim. There is no `"worktree"` value on the wire. | The admission rule below decides what is stored |
| `branch` | The short branch name, or `null` | The projection rule below, applied to the stored `observed_branch` at read time |
| `managed_by_baude` | Unchanged by this plan | Still the stored flag; with `role` it is the whole input to core's directory decision |

**Admission rule** (what `record_checkout_intent` and `record_runtime` store as `role`):

- `main` when all three hold: git discovery succeeded for the session's working directory;
  `snapshot.selected_worktree.path == snapshot.main_worktree`; and no checkout row of that repository
  already holds `main`.
- `managed_branch` in every other case, including the arm where discovery returned nothing (a plain
  folder; that arm is 21-10's and is left exactly as it is).
- `primary_default` is never assigned by daemon admission. It reaches daemon state only through core
  activation or a restored state file, and is served verbatim when present.

The path comparison is the one the daemon already makes for legacy sessions
(`bauded/src/manager.rs:162`) and core makes on activation (`baude-core/src/lifecycle.rs:2392`). The
third condition is not optional: `RepositoryState::validate` rejects a second `Main` in one
repository (`baude-core/src/repository.rs:1019-1028`), so without it a second plain session on the
same main checkout would fail every later save. The TUI's admission carries the same guard
(`baude/src/app.rs:2607`).

**Projection rule** (what `Manager::rows` serves as `branch`):

- A stored value beginning `refs/heads/` is served with that one leading prefix removed and the rest
  verbatim, so `refs/heads/chore/workspace` reads `chore/workspace`. The remainder is never split on `/`.
- Any other stored value is served verbatim. The daemon does not guess at a ref it does not recognize.
- No stored value is served as `null`. A detached HEAD stores none, because `WorktreeRecord.branch`
  is `None` exactly when `detached` is set (`baude-core/src/git.rs:13-20`, enforced at `:193`). There is
  no fallback to a default branch.
- The stored `observed_branch` is **not** rewritten. Core compares and re-observes full refs
  (`baude-core/src/lifecycle.rs:529`), so normalization lives in the projection only.

The value is the branch observed at admission or at core's last re-observation. This plan makes no
freshness claim beyond that.

**What decides whether a directory is deleted** is neither label. It is
`baude_core::removal::disk_action_for` (`baude-core/src/removal.rs:1088-1093`): a `Main` row is always
kept; any row with `managed_by_baude` false is always kept; only a non-`Main` row with the flag set is
removed. The admission correction can therefore only move a row toward "kept", and clients read the
outcome from the preview report's `paths_deleted` / `paths_kept`, never from `role`.

**How the tests know the expected value.** For any checkout row, the expected `branch` is the trimmed
stdout of `git -C <row path> symbolic-ref --short -q HEAD`, and `null` when that command exits
non-zero. The expected stored ref is the stdout of `git -C <row path> symbolic-ref -q HEAD`. The
expected `main` row is the one whose `path` is the directory the fixture cloned or initialized. No
test in this plan compares against a branch literal it did not read back from git.
</wire_contract>

  `git worktree remove` in a terminal. The re-run must converge. Asserted by
  `row_kinds_parent_removal_converges_after_the_worktree_was_removed_by_hand`.
