Design, from research; names may differ, behaviour may not:
- `Manager::begin_removal(&mut self, previewed) -> Result<RemovalInFlight, RemoveRowsError>` under the lock: persistence-blocked check, repository or folder reservation, fresh preview recheck, collect the row runtimes, `removal::prepare`; on a prepare error restore the runtimes and return it.
- Stage 2, no lock: one `std::panic::catch_unwind(AssertUnwindSafe(|| { test pause; removal::stop_and_delete(..) }))`. The `#[cfg(test)]` pause runs inside that closure, ahead of `stop_and_delete`, never before or outside it, so a panic the pause raises is caught exactly as one from the kill or the delete; plan 22.1-11 relies on this layout and Task 3 pins it. The runtimes stay owned by the in-flight value whatever happens.
- `Manager::finish_removal(&mut self, inflight, stage2) -> Result<RemovalReport, RemoveRowsError>` under the lock: a panic or an error restores every runtime and returns 500, a panic as a new `RemoveRowsError` variant whose body names the panic message; on success build the save closure and call `removal::commit`. When `commit` returns an error, which is a persist failure answered 503, `SelectionChanged` or a validation error answered 500, restore every runtime handle to the registry, clear `atomic_failure_for_test`, set `persistence_dirty` and `persistence_error` on a persist failure, and return before any publish, exactly as the error arm of today's `remove_rows`. On commit success run registry cleanup, permission wake-ups, persistence flags and the single `publish`, exactly as `remove_rows` does today. The reservation guards are fields of the in-flight value and drop when `finish_removal` returns, after the publish.
- `execute_removal`: under `#[cfg(test)]` capture redirects, then `tokio::task::spawn_blocking(move || { install redirects; stage 1 with the lock; stage 2 without; stage 3 with the lock; build the Response, the busy bodies resolved under the lock })`, then a `JoinError` maps to 500 `removal task failed: ...`. The `MutexGuard` never crosses an await.
- `#[cfg(test)]` removal pause on `Manager`: `pause_removals_for_test()` returns a cloneable handle; each removal entering stage 2 counts itself as entered and waits for release with a 10 s bound, recording a timeout; the handle can wait until N removals entered, release all, report whether any timed out, and arm a panic after release.
- Test helper in `api.rs` tests: capture redirects on the test thread, start a `std::thread` that installs them, waits for N entrants, records whether `shared.try_lock()` succeeded, treating only `WouldBlock` as held, then, only if free, runs the given probe on its own current-thread tokio runtime with each request under a 2 s `tokio::time::timeout` and an `Instant` check, then releases the pause and returns both. The removal itself is driven from the test body so its handler captures the test thread's redirects.
