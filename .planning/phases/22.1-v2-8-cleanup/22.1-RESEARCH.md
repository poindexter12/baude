## Summary

Four independent work items, each small in code but each resting on a non-obvious fact found this session.

**WR-06 is the only item with real design risk.** Today `execute_removal` takes the global `std::sync::Mutex<Manager>` and calls `remove_rows`, which calls `removal::remove(&mut self.repository_state, ...)` holding `&mut` state from row selection through kill, disk delete, save and clearing [VERIFIED: bauded/src/api.rs:176-177, baude-core/src/removal.rs:436-469]. Releasing the lock during kill and disk delete needs three things the code does not have yet: (1) `removal::remove` split into prepare / stop-and-delete / commit stages, where **commit re-derives the candidate from the live state** rather than reusing the one built before the window, or a concurrent admission in another repository is silently reverted; (2) an exclusion for paths the repository reservation does not cover today, namely **standalone removals (no reservation at all)** and **plain `POST /sessions` into an existing repository (no reservation)**; (3) the whole removal body running inside one `spawn_blocking` closure with the test thread's fixture redirects re-installed on the blocking thread, because every fixture redirect is thread-local and core's disk stage panics on an unredirected path in test builds.

**Suppression sync is a one-function change plus tests.** The TUI keys its lift on `git::repo_root(path)` falling back to the path; the daemon lifts the stored row path verbatim [VERIFIED: baude/src/app.rs:2507-2512, bauded/src/manager.rs:1606-1610]. They agree for every row whose stored path is a worktree root, and disagree for one shape only the daemon stores: a plain admission of a **subfolder** stores the subfolder as `observed_path` [VERIFIED: bauded/src/manager.rs:1710-1717, 1981]. That gives a genuine red-then-green test for the shared function. The store is shared only when both processes resolve the same config dir and workspace; the compose deployment keeps its own.

**Test hygiene root cause is not what the decision text assumes.** Reproduced this session: the four tests leave `sleep 30` processes whose **process group is their own pid, not the recorded group**, with session id equal to the dead PTY leader [VERIFIED: probe output below]. The gate runs the command under an interactive shell (`-il -c`), so job control moves `sleep` into its own group, and `trap '' HUP` keeps it alive when the leader dies. A guard that only kills the recorded process group would not catch them; the guard must also sweep the recorded **session**. A full run of the `baude` crate also left a fifth stray `sleep 30` from a TUI suppression test and 90 fixture dirs, so the four named tests are not the whole set and an outside-the-process check is needed to prove "nothing left behind". Fixture-dir leaks come from roughly 85 `temp_dir()` sites, most without a `Drop`.

**PWA is two small, already-prepared changes.** `renderRowsList` already supports a `keyless` option that renders the `other sessions` heading with no remove control, and has a test for it; `app.js` just never passes it [VERIFIED: bauded/web/removal-controller.js:549-554, bauded/web/app.js:715-728]. The title is one line in `confirmationView` [VERIFIED: bauded/web/removal.js:223]; a checkout target with a non-empty `paths_deleted` is always a managed worktree by core's disk rule, so "Remove this worktree and delete its folder?" can be produced from the report alone.

**Primary recommendation:** Split core removal into `prepare` / `stop_and_delete` / `commit` with `remove` kept as their composition; run the daemon's three stages inside one `spawn_blocking` closure with two short lock scopes; extend the exclusion to standalone rows and plain admissions; add a test-only pause seam so the "served during the slow stage" and "503 on the same repository" tests are deterministic.

### Item 1: WR-06, removal without holding the manager lock

#### What the code does today

```text
POST /removals ── async handler ── lock(&state) ─────────────────────────────── guard dropped
                                   │ remove_rows(&previewed)
                                   │   persistence_blocked? ─► 503
                                   │   reserve(repository)  ─► Busy 503   (standalone: no reservation)
                                   │   preview recheck      ─► 409 drift / 404
                                   │   collect_row_runtimes (Sessions moved out of self.sessions)
                                   │   removal::remove(&mut repository_state, ...)
                                   │       select, plan, preflight, candidate+validate
                                   │       KILL (seconds)  ─► 500 survived
                                   │       DISK (seconds)  ─► 500 disk
                                   │       save(candidate) ─► 503 persist
                                   │       clear stage (bindings, markers, suppression)
                                   │   on Err: restore_row_runtimes
                                   │   on Ok: registry cleanup, publish(rows_removed)
```

Verbatim anchors:

- Reservation: `self.repository_reservations.reserve(repository).map_err(|_| RemoveRowsError::Busy(repository))?` [VERIFIED: bauded/src/manager.rs:1134-1141]

#### Core split (baude-core/src/removal.rs)

Names are a recommendation; the shape is what matters.

```rust
// Recommendation. Signatures only; bodies are the existing stage functions.
pub struct PreparedRemoval { set: RemovalSet, planned: Vec<ClearedItem> }
pub struct StageEffects { killed: Vec<KilledRuntime>, disk: DiskResults }

/// select_rows, planned_clearings, preflight, candidate build + validate_for_save
/// (candidate discarded: validation must still refuse before any irreversible effect).
pub fn prepare(state: &RepositoryState, target: RemovalTarget, runtimes: &[RowRuntime])
    -> Result<PreparedRemoval, RemovalError>;

/// kill_stage then disk_stage. Reads no RepositoryState. Safe to run without any lock.
pub fn stop_and_delete(prepared: &PreparedRemoval, runtimes: &mut [RowRuntime])
    -> Result<StageEffects, RemovalError>;

/// Re-derive the candidate from `*state` NOW: clone, remove_rows(set keys), check the
/// target still selects exactly the prepared rows, validate_for_save, persist_stage
/// (one save), clear_stage, report_from_set. `*state` untouched on Err.
pub fn commit(state: &mut RepositoryState, prepared: PreparedRemoval, effects: StageEffects,
              runtimes: &mut Vec<RowRuntime>, save: impl FnOnce(&StateFile) -> Result<(), SaveError>)
    -> Result<RemovalReport, RemovalError>;

/// Unchanged signature and behaviour; the TUI keeps calling this.
pub fn remove(state, target, runtimes, save) -> Result<RemovalReport, RemovalError> {
    let prepared = prepare(state, target, runtimes)?;
    let effects = stop_and_delete(&prepared, runtimes)?;
    commit(state, prepared, effects, runtimes, save)
}
```

The commit-time re-select check: if `select_rows(state, target)` no longer yields the prepared row keys, the exclusion was broken. It returns an error and leaves `*state` untouched. That error follows an irreversible effect, so it must be unreachable under correct exclusion; recommend a new `RemovalError` variant so the exhaustive `match` in `api.rs::removal_error` forces a deliberate 500 mapping. Unit-testable in core by mutating the state between `stop_and_delete` and `commit`.

Why:
- The gate execs `"$BAUDE_GATE_SHELL" -il -c "$BAUDE_GATE_COMMAND"` (bash variant: `--noprofile --norc -i -c`) [VERIFIED: baude-core/src/pty.rs:171, 182]. An interactive shell has job control on, so the `sleep` of a multi-command string runs in **its own process group** (pgid = its pid). The repo already knows this: another test notes "`set +m` is load-bearing: the gate runs `bash -i`, and job control" [VERIFIED: pty.rs:2090].
- All four commands start with `trap '' HUP` [VERIFIED: pty.rs:1539, 1703; session.rs:1437], which `sleep` inherits, so the kernel's SIGHUP on leader death does not kill it.
- `Pty::kill()` signals the leader only, through portable_pty, then reaps it [VERIFIED: pty.rs:669-677]; `kill_and_wait()` SIGTERM/SIGKILLs the **recorded** group [VERIFIED: pty.rs:874-884, 1073-1076]. Neither reaches a different group. The tests pass because they assert only that the leader is not a zombie.
- The session id survives: every leaked `sleep` still has `sid` = the dead leader's pid, which the PTY recorded as `identity.session` (the registration test asserts `identity.pid as i32 == identity.session`) [VERIFIED: pty.rs:1550-1553].

So a guard that "kills and reaps the fixture process group" must kill the recorded group **and every process whose session id is the recorded session**. On macOS `pgrep` has no `-s` and `ps -o sess` prints 0 [VERIFIED: probe this session], so enumerate pids with `ps -eo pid=` (already used by tests on both platforms, pty.rs:1995) and compare `libc::getsid(pid)`; `getsid` on another session's process works on macOS [VERIFIED: probe returned the sids above].

Safety rule for the guard: refuse to sweep unless the recorded session equals the recorded leader pid (the PTY child called `setsid`). Otherwise a bug could sweep the test harness's own session.

Production note, not in scope: KILL-02's scope note already puts processes outside the recorded group outside the kill unit (REQUIREMENTS.md KILL-02 scope). Do not change `kill_and_wait`.

### Anti-Patterns to Avoid
- **Committing the stage-1 candidate:** reverts any admission or removal in another repository that landed during the window.
- **Awaiting the slow stage from the async task and committing there:** a client disconnect drops the handler after kill and delete, so restore or commit never runs.
- **Holding the manager guard across `.await`:** `std::sync::MutexGuard` is not `Send`; take it only inside the blocking closure.
- **Adding a "removing" state to `/rows`:** wire contract; the all-or-nothing tests define the window as "pre-removal shape".
- **Killing by recorded group only in the test guard:** misses job-control children (verified).
- **Asserting on source text** for "both sites call one function": CLAUDE.md forbids it; the subfolder admission test proves it behaviourally.

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: Thread-local fixture redirects do not cross to the blocking thread
**What goes wrong:** In tests, `git::worktrees_base()`, `persist::config_dir()` and `workspace::active()` panic on the blocking thread ("resolved to the real user path" / identity escape), or the disk stage refuses the managed path.
**Why:** `REDIRECTS` is a `thread_local!` and `TestRedirect` is deliberately `!Send` [VERIFIED: baude-core/src/testing.rs:85-115]; `workspace::active()` in test builds panics without the override [VERIFIED: baude-core/src/workspace.rs:455-463]; the disk stage calls `managed_root_contains` → `worktrees_base()` [VERIFIED: baude-core/src/git.rs:3062-3064, 3480]; clear stage reads `persist::config_dir()` [VERIFIED: removal.rs:671]. The existing race tests even say "the fixture's containment redirect is thread-local and a worker thread would escape it" [VERIFIED: bauded/src/api.rs:4434-4436].
**How to avoid:** Add to `testing.rs` a `pub fn capture() -> Redirects` (wrapping the private `current()`) and `TestRedirect::install(Redirects) -> TestRedirect`. In `execute_removal`, `#[cfg(test)]` capture before `spawn_blocking` and install as the first statement inside the closure. `Redirects` is `Clone` and holds `PathBuf`s and a `&'static Workspace`.
**Warning signs:** Panics containing `ESCAPE_PANIC_MARKER` only in the new tests.

### Pitfall 2: Uncovered mutation paths
**What goes wrong:** A plain `POST /sessions` adds a child to a repository mid-removal, or reopens a standalone row being removed and spawns a runtime that the commit then orphans.
**How to avoid:** The exclusion matrix above; tests 2 and 3.

### Pitfall 3: Panic or disconnect loses the runtime handles
**What goes wrong:** `Session`s moved out of the registry are dropped with the panicking closure; rows keep `runtime_checkouts` entries pointing at nothing.
**How to avoid:** `catch_unwind(AssertUnwindSafe(...))` around stage 2 returning the `Vec<RowRuntime>` in every case; run stages 1–3 in one `spawn_blocking` so a dropped handler future cannot skip stage 3; map a `JoinError` to 500.

### Pitfall 4: `/rows` shape changes during the window
**What goes wrong:** `rows()` merges live metadata from `self.sessions` [VERIFIED: manager.rs:1337-1342, 1020-1028]. With the doomed sessions moved out, a row shows its stored `RetainedSessionState` (for example `archived: false` after a live archive) until commit, a third shape the race tests forbid in principle.
**How to avoid:** In stage 1, before moving sessions out, apply `merge_live_runtime_metadata` for the doomed rows into `self.repository_state` (it is what the next save would write anyway [VERIFIED: manager.rs:220-245]). Test 8.

### Pitfall 5: Stale survivor overrides at commit
**What goes wrong:** Today the save closure uses overrides snapshotted before the core call [VERIFIED: manager.rs:1158-1159]; reusing a stage-1 snapshot after the window writes stale metadata for survivors renamed or archived meanwhile.
**How to avoid:** Compute `survivor_runtime_overrides()` and `standalone_runtime_overrides()` in stage 3.

### Pitfall 6: Worktree-create busy is a 400 today
`activate_branch_worktree`'s Busy outcome becomes `anyhow!` → `Domain` → 400 [VERIFIED: manager.rs:1647-1648; api.rs:118-125, 254-260]. CONTEXT requires 503; add a typed busy variant. README endpoint table and the 503 row of the removal status table (README.md:990) need updating.

### Pitfall 7: The hygiene guard must never sweep the harness's session
Gate on `session == leader pid` before any session-wide kill.

### Pitfall 8: Process-cwd check path forms
macOS `lsof` reports `/private/var/...`; compare canonical paths, or the check passes with leaks present.

### Pitfall 10: The leftover-check TMPDIR must be outside every git work tree
**What goes wrong:** With `TMPDIR` under the repository checkout, `standalone_admission_dedup_close_reopen_and_missing_are_durable` and `standalone_reopen_of_resume_id_without_transcript_continues_and_clears_it` failed with `unexpected selection` [VERIFIED: target/gsd-221/suite-run/suite.log lines 1762-1768].
**Why:** Their "standalone" folders live under `temp_dir()`; inside a git work tree, `git rev-parse --show-toplevel` finds the enclosing repository and the folder is admitted as a checkout.
**How to avoid:** Derive the suite `TMPDIR` from `mktemp -d "${TMPDIR:-/tmp}/..."` (gate) and `${{ runner.temp }}` (CI), never from a path under the checkout or `target/`. The self-test of the new script can assert the directory is not inside a git work tree.

### Pitfall 9: Commit messages
No nested parentheses in commit bodies or PR titles (release-please). Threat IDs like `T-21-14` are fine; avoid `(see (T-21-14))`.

## Open Questions

1. **Id-addressed mutations on a doomed session: 404 or 503?**
   - Known: with handles moved out, `DELETE /sessions/{id}`, `restart`, `archive`, `unarchive` answer 404 "no session" during the window.
   - Unclear: CONTEXT says "any request touching the repository being removed gets 503 Busy".
   - Recommendation: return 503 for those four mutating routes by checking, under the lock, whether the id's row is reserved (a reservation visible under the manager lock can only belong to an in-flight removal); keep 404 for read and I/O routes. Small and matches CONTEXT.
2. **Daemon subfolder rows and the shared key.** The decision says "repository root or the canonical path". A subfolder row's own removal entry is keyed on the subfolder and the shared key cannot lift it. Recommendation: document as inert (README footnote not needed; RESEARCH and SUMMARY only), do not change the writer.
3. **Archived unclaimed sessions:** under `other sessions` (archived last) or under the existing `archived` heading? Recommendation: under `other sessions`, archived last, since the card already carries the archived class; one heading means "no remove control here".
4. **Standalone reservation home:** daemon-only (`bauded/src/manager.rs`) or core next to `RepositoryReservations`? Recommendation: daemon-only; the TUI is single-threaded and does not need it.
