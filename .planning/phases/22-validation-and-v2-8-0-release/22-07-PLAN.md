Design, decided from the code.
- The fact "the user removed this repository's primary" lives on the entry removal already writes for that row, as a new `primary` flag.
  - Not the state file: every state struct is `deny_unknown_fields` (`baude-core/src/repository.rs`, 14 from line 61), so a new member is a schema bump. The store is additive by design (`suppression.rs:37-38`).
  - `update_suppression` (`removal.rs:777-806`) holds the removed row with its role and writes the entry with the parent's common dir (`suppression.rs:51-53`). A managed primary is deleted from disk (`removal.rs:1088-1092`); its entry is written all the same, and a query by repository needs no live path.
  - The fact leaves only with its entry, Phase 19 D-12 unchanged: `lift` of that exact path (`suppression.rs:84-94`), or `drop_children` when the repository row is removed (`suppression.rs:113-130`, called at `removal.rs:763`).
  - Removal is shared code, so a removal through the daemon records the fact with no edit under `bauded/`. The daemon never derives: `git::ensure_default_worktree` has one caller, `app.rs:2633`.
- The consult. `admit_repository` takes only a path (`app.rs:2514`); launch, `n` and `c` all reach it through one funnel (`6573`). It cannot tell a launch from `n`, but it knows which folder was named: `lift_suppression` (`2518`) runs first, keyed by that folder's own root (`2508`). When the repository has no `PrimaryDefault` row (`2585-2593`), before `allocate_checkout_key` (`2626`) and `ensure_default_worktree` (`2633`, which can run `git worktree add`), ask whether an entry of this repository carries the fact. If one does, derive nothing.
- Routes. Launching inside the removed folder, `n` naming it and `c` into it lift its entry at `2518`, the fact with it, and derivation runs in the same pass. Naming a sibling lifts nothing of the primary's.
- Folder deleted. No route can name a folder that is gone. Two ways back, with no new mechanism: put a worktree back at that path and open it, which is the exact-path lift; or remove the repository row, which drops the entry, and admit the repository again.
- Not the trigger: "repository row without a primary". That state also follows a failed default-branch resolution (`2567-2582`), where the next admission must derive.
- An entry written before this plan has no flag: it loads, keeps its path out of the sweep and does not stop derivation. The store has never shipped (absent from `v2.7.3` and `origin/main`), so nothing is migrated.
